# 当前训练写链路压测与优化

日期：2026-09-17（Asia/Shanghai）。这次实验回答“当前写链路哪里慢、改动是否有效”，范围是应用 Service 加 PostgreSQL 的真实事务调用，不是生产容量承诺。

## 结论

瓶颈出现在同一训练的加组事务：`WorkoutService.addSet` 已经先锁住 `workout` 父行，随后 `nextSetNumberForUpdate` 又对同一训练动作执行一次 `workout_exercise ... FOR UPDATE`。父行锁已经串行化该训练的所有写入，子行锁不再增加正确性，却增加了一次数据库往返。

优化只保留父训练锁，并将取号方法改为 `nextSetNumber`；同时删除不再使用的子表锁 Mapper。优化后同一训练 192 并发写入的吞吐从 **282.64** 提升到 **332.25 RPS（+17.56%）**，P95 从 **134.81 ms** 降到 **116.96 ms（-13.25%）**，P99 从 **228.67 ms** 降到 **170.38 ms（-25.47%）**。离线回补的 P95 从 **208.13 ms** 降到 **162.20 ms（-22.07%）**。多用户加组没有正向变化，说明这次改动只改善锁串行路径，没有把局部结果夸大成全局吞吐提升。

## 固定条件与负载

- Windows 11，32 逻辑处理器，Java 25.0.2，Docker Engine 29.7.2。
- 每轮使用全新 PostgreSQL `pgvector/pgvector:pg17` 与 Redis `7.4-alpine` Testcontainers；Flyway v20 完成迁移。
- Hikari 最大连接 16、最小空闲 4，固定并发 32；每 50 ms 采集数据库活动连接、锁等待、Hikari 等待连接线程和 JVM 堆使用。
- 多用户加组：24 个用户、384 次独立写入。
- 同一训练并发写入：同一训练、192 次独立写入，观察父行锁串行化和唯一组号。
- 离线回补：96 个 `Client-Operation-Id`，每个操作额外重放 2 次，共 288 次请求；之后完成训练，检查回执、组数和 Outbox。
- 预热使用独立训练数据；基线和优化轮次使用相同参数。事件 Relay 关闭，只验证完成事务写入 Outbox，不把 Kafka 消费时间混入写入 P95。

## 前后结果

| 场景 | 指标 | 基线 | 优化后 | 变化 |
|---|---:|---:|---:|---:|
| 多用户加组 | 吞吐（RPS） | 1526.65 | 1509.99 | -1.09%（运行波动） |
| 多用户加组 | P95 / P99（ms） | 33.65 / 43.04 | 36.02 / 50.22 | 未改善 |
| 同一训练并发写 | 吞吐（RPS） | 282.64 | 332.25 | **+17.56%** |
| 同一训练并发写 | P95 / P99（ms） | 134.81 / 228.67 | 116.96 / 170.38 | **-13.25% / -25.47%** |
| 离线回补 | 吞吐（RPS） | 337.32 | 391.48 | **+16.06%** |
| 离线回补 | P95 / P99（ms） | 208.13 / 219.29 | 162.20 / 166.22 | **-22.07% / -24.16%** |

两轮所有场景错误数均为 0。同一训练场景两轮最高锁等待均为 14，最高 Hikari 等待连接线程为 16/17；锁等待没有消失，因为它是保护同一训练顺序的必要成本，本次优化减少的是每个事务的额外 SQL 往返。离线场景两轮均得到 96 行、96 条回执、1 个完成事件和 1 条待发 Outbox，证明重放没有重复写入，完成事件没有重复产生。

## 面试回答

“我先把加组、同训练并发写和离线回补拆成三类负载，在固定 16 连接、32 并发的 PostgreSQL Testcontainers 中采集 P95/P99、锁等待、连接池和数据护栏。基线发现同训练写的尾延迟最高，代码检查确认每次写先锁 `workout` 父行，取组号时又重复锁 `workout_exercise` 子行。父行锁已经保证同一训练内串行和组号正确，子锁只增加一次往返，所以去掉它并保持数据库唯一约束和父行锁。复测同条件下同训练吞吐提升 17.56%，P99 下降 25.47%；离线回补 P95 下降 22.07%，96 条记录重放后仍是 96 行、1 个完成事件。代价是这个优化依赖所有训练写入口遵守父行锁协议，因此我保留并发正确性测试和唯一约束作为护栏；多用户场景未改善，我没有把结果写成全局容量提升。”

## 边界与后续

这是隔离 Testcontainers 的 Service 级压测，尚未覆盖真实 HTTP、多实例、生产机器 CPU/磁盘、Kafka Relay 恢复速率或长期 Outbox 积压。下一项仍是用真实 Embedding 做检索质量、延迟和成本评测；不继续增加中间件。
