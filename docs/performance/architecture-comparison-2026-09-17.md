# Kafka、缓存与检索：简单方案对照结果

**结论：本次证明了异步接受与热点 L1 的局部收益，没有证明 Kafka 相对 PG worker 的性能必要性，也没有证明默认哈希向量的混合检索优于 BM25。** 冷缓存负收益和无答案返回候选均保留在结果中。

本次没有模拟真实用户分布、并发 HTTP、独立应用进程、长期资源曲线或生产部署；结果不转换为 QPS/容量保证。

## 2. 事件：异步能更早返回，Kafka 并不自动更快

每轮 20 次完成请求，每次 1 个动作、1 个工作组、重量 80×5。每种方案先恢复相同空夹具，再预热一次；核对每次得到 4 条 PR、4 条通知及容量 400。同步组在完成事务中处理派生；异步组全部请求提交后再启动 worker。表中各项依次为第 1/2/3 轮，单位 ms。

| 路径 | 完成请求 P95 | 批次提交后的追平时间 | 批次接受至追平总时间 |
|---|---|---|---|
| 同事务同步派生 | 47.32 / 29.14 / 28.12 | 1.98 / 0.81 / 1.42（只剩空队列检查） | 745.49 / 517.56 / 501.56 |
| PG 任务 worker | 10.71 / 7.72 / 6.61 | 608.68 / 545.98 / 533.25 | 789.94 / 684.20 / 651.39 |
| Kafka 分发 | 9.21 / 7.93 / 7.57 | 802.78 / 685.69 / 692.91 | 959.75 / 821.73 / 824.45 |

数据：[events.json](evidence/architecture-20260917-final/events.json)，含逐请求时延和 P99。每轮仅 20 次请求，P95 是第 19 个排序样本，P99 是最大值，尾延迟统计很粗糙；三轮也存在预热/运行时波动，不计算夸张提升百分比。

**观察与解释：**

1. 异步组接受请求较快，但工作被移到后面，并没有消失。本次串行批次的总耗时反而同步组较短；不能把接口早返回当成系统完成更多工作。
2. Kafka 接受阶段与 PG 相同，都只提交 Workout + Outbox。两组接受延迟差异不能归功于 Broker，因为此时尚未分发。
3. PG worker 三轮追平都比 Kafka 实验分发快。本次多一跳 Broker、轮询和提交位点有成本；不支持“为了性能必须 Kafka”。
4. 数据库触发器拒绝 Analytics 投影时，同步完成事务回滚，训练仍是 IN_PROGRESS；PG 异步路径的训练已是 COMPLETED，任务失败后重领并恢复，最终 PR/通知不重复。该结果证明异步隔离的价值，不是 Kafka 停机演练。

**公平性边界：** 同步组为了共用真实业务代码保留 Outbox/Inbox，不是最轻量的同步 CRUD；PG 组复用 Outbox 为任务表，未另实现生产 worker。Kafka 组复用现有 Relay，但使用单个实验消费者分发两个 topic，并非线上三个消费组的吞吐实验。所有方案复用相同投影处理器，因此这是执行位置和传输成本的局部对照。

**决策：** 当前小规模任务，PG worker 是合理的简化候选。Kafka 的采用条件应是独立消费者推进、回放和规模扩展需求；这些价值需要独立消费组及负载实验补证。本次不切换线上架构。

## 3. 缓存：热命中显著受益，冷回源需要支付成本

同一张 1000 行表、同一主键 SQL、256 字符值。两个独立缓存对象交替调用，模拟两份 L1；热场景预热 20 个键后读取 600 次，冷场景依次读取 600 个不同键。Redis 单层通过 L1 立即过期实现，保留相同序列化及重建策略。

| 场景 / 方案 | 三轮 P95（ms） | 每轮数据库 loader 次数 | 每轮 L1 命中 |
|---|---|---|---|
| 热 / PG 直读 | 0.6680 / 0.5965 / 0.5534 | 600 | 0 |
| 热 / Redis 单层 | 0.9105 / 0.5553 / 0.6003 | 0 | 0 |
| 热 / L1+L2 | 0.0030 / 0.0021 / 0.0014 | 0 | 600 |
| 冷 / PG 直读 | 0.5814 / 0.5451 / 0.5565 | 600 | 0 |
| 冷 / Redis 单层 | 3.5564 / 2.8925 / 2.8854 | 600 | 0 |
| 冷 / L1+L2 | 3.0667 / 2.8951 / 3.0181 | 600 | 0 |

数据：[cache.json](evidence/architecture-20260917-final/cache.json)，保留 10,800 个计时样本及配置。**这些是 JVM 内顺序调用耗时，不是 HTTP 接口耗时；微秒级 L1 数字不能写成全系统响应时间。**

- 热 L1 确实省去网络访问；Redis 能消除重复数据库 loader，但对这个本地小表查询，时延未稳定优于 PG。低负载时“减轻数据库查询次数”与“用户明显更快”是两回事。
- 冷缓存时三种方案都回源 600 次；缓存路径增加 Redis 读取、锁、回填等工作，实测更慢。缓存不能无条件改善每个请求。
- A 更新数据库并删除自身 L1/共享 L2 后，B 仍读取到 L1 旧值；在默认 5 秒 TTL 下约 5053 ms 后观察到新值，包含轮询间隔。该场景验证跨对象短 TTL 收敛，不是全局最大陈旧窗口证明，也没有覆盖并发旧值回填。

**决策：** 热点展示可以保留两级缓存；低复用读和关键业务判断优先直读。保留 L1 的依据应是实际命中率、数据库压力与陈旧容忍度，而不是“Redis/Caffeine 都用了”。两个对象不等同真实多实例，本次未测应用扩容和 Redis 故障峰值。

## 4. 检索：当前诊断集未证明混合优于 BM25

固定现有 10 篇合成知识文档；新增 6 条术语、6 条改写表达、2 条无答案查询。每轮每方案执行同一 14 条查询，共 168 次测量。单路真正跳过关闭的通道；RRF 与重排分别比较，保持相同切分。默认使用本地确定性哈希向量。

| 方案 | 术语 Hit@5 / MRR | 改写表达 Hit@5 / MRR | 全部查询时延 P95（ms，42 次合并） |
|---|---|---|---|
| BM25 | 6/6 / 1.0000 | 6/6 / 0.7833 | 18.88 |
| 哈希向量 | 6/6 / 1.0000 | 6/6 / 0.5333 | 2.15 |
| RRF 混合 | 6/6 / 1.0000 | 6/6 / 0.7556 | 22.32 |
| 混合 + 当前规则重排 | 6/6 / 1.0000 | 6/6 / 0.7833 | 19.16 |

数据：[retrieval.json](evidence/architecture-20260917-final/retrieval.json)，含每个样本排名、来源、耗时、真实检索模式及 profile。表中质量用唯一查询样本计算；三轮确定性结果一致，不把三次重复当成三倍独立质量样本。

- 仅 10 篇文档而取 Top5 很宽松，所有可回答样本都 Hit@5，不能据此声称真实质量 100%。MRR 显示当前混合未超过 BM25；不满足实验卡中“改写表达相对两个单路都有净收益”的采用条件。
- 无答案查询在四种方案下都返回候选（每方案每轮 2/2）。这是检索候选返回，不是模型生成了错误答案；但说明检索接口本身没有证明拒答能力。
- 数据由作者根据语料编写，没有据结果调参，但不是独立人工留出集；也没有人工评估引用支撑。哈希向量延迟低不代表真实 Embedding 的成本或语义能力。

**决策：** 维持 BM25 简单基线；真实语义模型、独立标注与索引重建后才能判断双路必要性。当前线上仍默认双路，本次只补齐离线消融，没有更换模型或改变线上默认检索策略。
