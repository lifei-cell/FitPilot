# 架构对照实验卡

日期：2026-09-17。基线 `90dfffa`；实际运行以 manifest 中提交与源码 SHA-256 为准。此卡在首次测量前固定；不能看完结果再改门槛。

## 范围和预设判断

本次是可执行的机制对照，不替代[完整设计取舍验证计划](../test-plans/设计取舍验证测试计划-2026-09-17.md)里的多实例压测、资源曲线、真实 Embedding 或用户研究。全部依赖由 Testcontainers 新建，使用合成数据；不调用外部 AI Provider，不连接现有业务数据库。实验类刻意不命名为普通 Test/IT，以显式脚本执行，不向每次质量门禁混入时间不稳定的基准测试。

| 实验 | 对照与固定条件 | 主指标 / 护栏 | 预设判定 |
|---|---|---|---|
| 事件 | 同事务派生 / PG 任务 worker / Kafka 分发；20 次独立用户训练完成为一批，3 轮轮换执行顺序，每条路径先预热一次 | 接受请求 P95、批次追平时间；每训练 4 条 PR、4 条通知、容量 400，不能重复或丢失 | 任一业务核对失败即实验失败；异步接受延迟下降只归因于解耦，Kafka 相对 PG 的收益必须单独比较。20 样本 P95/P99 波动较大，不推断系统容量 |
| 缓存 | PG 直读 / Redis 单层 / L1+L2；同一 SQL、256 字符 payload、1000 行；两套独立 L1 对象交替访问；热场景 20 键预热后 600 请求，冷场景 600 个不重复键，随机种子 917，3 轮轮换 | P95、实际 loader SQL 次数、L1 命中；返回值正确，跨对象旧值能在配置 TTL 后收敛 | 只有热场景时延与数据库回源优势可重复才可报告该场景收益；冷场景负收益必须保留。两个对象不等同两个进程；不宣称生产缓存必要性 |
| 检索 | BM25 / 向量 / RRF / RRF+当前重排；同一 10 篇既有合成语料与冻结的 14 条诊断查询，每种先预热全部查询，3 轮轮换 | 单正确来源 Hit@5、MRR、P95、无答案查询返回内容情况；0 权重的通道不能发起调用 | 需在同义表达类相对两个单路均有净收益，才能支持这个诊断集上的混合增益；失败则报告“未证明”。同样的确定性查询重复运行只衡量时延波动，不增加独立质量样本量 |

检索只有一个标注正确来源时，Hit@5 与该样本 Recall@5 相同；不把引用 URL 命中当成答案正确或引用支撑结论。查询由本次作者按现有语料编写，未据结果调参，仍不是独立人工留出集；无真实语义模型时不得声称解决了同义词理解。

## 对照实现边界

- 事件复用真实 `WorkoutService.complete`、Outbox/Inbox 和 PR/Analytics/Notification 处理器，改变派生执行的位置。同步组保留了 Outbox/Inbox 开销，不是精简 CRUD 的最佳性能；PG 组以既有 Outbox 充当任务表，并非新增生产 worker。Kafka 组用真实 Broker、现有 Relay 和单个实验消费者调度相同处理器，不能代表线上多消费组并行吞吐。
- 异步组先接受完整批次，再启动派生，测量接受延迟和批次恢复；不把没有并行竞争的接受延迟当成稳态压测结果。PG 和 Kafka 均采用这一顺序，不人为给简单方案添加延时。
- 每种事件方案开始前清空隔离容器内的用户、训练与事件夹具并重置序列，使数据库初始数据量相同；Kafka 实验消费者从前次测量后的末尾开始，不回放前次样本。计时在业务核对之前停止。
- 同步与 PG 的下游故障通过真实数据库触发器拒绝分析投影，验证核心训练回滚/保留及恢复；不是 Kafka 停机测试。现有 `FitPilotEventFlowIT` 和 `OutboxLeaseIT` 另行提供消息重复、毒消息及领取故障证据。
- Redis 单层在实验中使用 L1 立即过期的同一 `TwoLevelCache`，保留相同序列化、空缓存和回源锁策略。没有增加线上开关。
- 单路检索将另一通道权重设 0，并真正跳过该通道的请求与候选；线上默认双路不变。语料切分保持相同，以免把切分收益混入检索消融。
- CPU/内存隔离、稳态并发、长时间 TTL 更新、数据库数据量阶梯、故障期间缓存回源峰值、独立进程失效传播、真实向量与人工引用审核不在本次测量范围。
