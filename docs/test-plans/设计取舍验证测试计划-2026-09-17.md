# FitPilot 设计取舍验证测试计划

日期：2026-09-17。范围：承接[设计取舍验证矩阵](../interview/10-设计取舍验证矩阵.md)，验证训练数据、异步事件、缓存、RAG、Agent 和交付设计的正确性、相对收益及成本。计划基于代码基线 `3b5290c` 和当时的脚本入口编写；执行时必须记录实际 SHA。本文件是**待执行计划**，不是测试通过报告。真实生产集群不在本计划的默认执行范围。

## 1. 判定原则与停止条件

2026-09-17 执行更新：E02/P01/A01 已有[局部机制对照及原始数据](../performance/architecture-comparison-2026-09-17.md)，事件测试适配器与缓存三路径已实现，单路检索可真正关闭另一通道。下文原计划的多进程压测、资源曲线及真实 Embedding 仍待独立执行，不将本次局部实验视为整份计划完成。

每个取舍分三层下结论：①业务不变量/故障恢复正确；②在相同条件下优于更简单的方案，且新增资源与运维成本可接受；③真实用户获得可观察收益。只通过第①层，可说“实现可用”，不能说“选型必要”或“产品有效”。

执行前填写实验卡：`假设｜简单方案｜候选方案｜主指标｜护栏指标｜预设门槛｜SHA｜环境｜样本/负载｜停止条件`。性能或 AI 结果若低于预设门槛、出现业务事实丢失/越权写入，或数据集污染，立即终止该实验并保留原始证据。不得在看到结果后修改门槛；若需要调整，开启新 Run ID。

| 门禁 | 统一判定 |
|---|---|
| 正确性 | 本计划列出的故障与并发场景中，确认过的组不丢失、不重复；私有数据不跨用户；未确认 AI 动作不写入；旧 Outbox 领取者不覆盖新状态。任何一条违反即失败。只声明覆盖过的场景，不推断全局零故障。 |
| 对照公平性 | 同一 SHA、数据集、硬件、负载、预热、测量时间和依赖版本；随机或交替运行对照顺序，至少 3 次独立重复。记录每次结果及波动，不只挑最好的一次。 |
| 性能 | 主指标预先选一个（如 Workout 完成 P95、DB CPU 或检索 Recall@5）；同时看 P99、错误率、dropped iterations、资源与成本。相对改善必须大于重复运行波动，且护栏不退化。绝对 SLO 在采集基线与目标用户场景后写入实验卡，不套用历史热点读数字。 |
| 用户研究 | 小样本只能说明可用性、具体痛点和下一步假设；留存、训练效果与因果收益需要更长观察或随机对照。疼痛反馈仅作产品安全信号，不作医疗效果声明。 |

## 2. 环境、数据与证据准备

1. **隔离环境**：使用独立 Docker Compose 数据库/Redis/Kafka/Elasticsearch 和测试账号；禁止对生产数据执行故障注入、压测或索引重建。记录 Windows/Docker/Java/Node 版本、CPU/内存、容器限制、数据库迁移版本、配置文件散列、应用 SHA 与镜像 digest（若使用）。Windows Testcontainers 设置 `$env:DOCKER_HOST = 'npipe:////./pipe/dockerDesktopLinuxEngine'`。
2. **质量基线**：依赖和 Playwright 浏览器已安装时运行 `./scripts/run-quality-gate.ps1 -SkipInstall -SkipBrowserInstall`；否则用不带跳过参数的脚本。要求 `QUALITY_GATE=PASS`，且 Surefire/Failsafe 零跳过；记录实际测试数，不沿用 V18/V20 历史数量。Web 包括 `web/e2e/quick-set.spec.ts` 与 `web/e2e-offline/recovery.spec.ts`。
3. **合成数据**：固定随机种子与生成器版本；至少覆盖空历史、一次训练、多月训练、多人高基数、热门动作及稀疏动作。分别准备 1/10/100 倍相对数据量，具体用户与训练条数在实验卡中固定。所有对照从同一数据库快照恢复，避免缓存预热和事件积压串扰。真实用户数据只在获得自愿同意后采集；导出前去标识化。
4. **负载**：记录到达率、读写比例、热键分布、并发用户数、预热时长、稳态与突发时长。现有 `load-test/run-v5.ps1` 只覆盖历史 V5 混合/突发脚本，不能直接代表 V19 离线回补；执行写链路与三方案对照前，先新增专用 k6 场景和配置开关/独立实现。现有报告不作为新结果。
5. **证据目录**：每次运行建立 `docs/test-results/<RunId>/` 或受控的忽略目录，存实验卡、脚本 SHA、配置脱敏快照、JUnit/Playwright/k6 原始输出、数据库核对 SQL、Prometheus 指标、人工标注、失败日志和总结。不得提交 JWT、运维 Token、真实提示词、个人资料或秘密配置。若原始数据不宜入库，文档只写可复核的相对路径、哈希和保管位置。

每份结果报告使用统一结构：`问题与反事实 → 预注册门槛 → 版本/环境/数据 → 步骤 → 原始结果与波动 → 失败样本 → 资源/运维成本 → 结论与适用边界 → 后续决定`。对业务正确性、工程收益、真实用户价值分别给出状态：`PASS / FAIL / NOT_RUN / INCONCLUSIVE`。当前仓库的 V18、V19、V20 和历史 V5 报告是复现入口，不自动成为本计划在新 SHA 上的通过证据。
