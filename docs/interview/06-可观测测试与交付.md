# 可观测性、测试、Docker、Kubernetes 与 CI/CD

## 1. 监控与可观测性的区别

监控通常回答已知问题，例如 CPU 是否超阈值；可观测性强调能否从系统外部输出推断内部状态，尤其用于未知故障。三大信号：

- Metrics：低成本聚合趋势和告警。
- Logs：离散事件和详细上下文。
- Traces：一次请求跨组件的因果链和耗时分解。

三者通过 Request ID、Trace ID、低基数业务标签关联。不是接入三个组件就自动“可观测”，关键是能否从告警定位到 Span 和日志，再找到可执行原因。

## 2. Micrometer、Prometheus 与 Grafana

Micrometer 是 JVM 指标门面，类似日志门面的定位；Prometheus Registry 暴露 `/actuator/prometheus`。Prometheus 采用 Pull 模型周期抓取时序数据，Grafana 查询并展示。

FitPilot 指标覆盖 HTTP、Agent、LLM、Tool、RAG、Outbox、Kafka Lag、数据库连接池和 AI 产品价值。

### Counter、Gauge、Timer、Histogram

- Counter：单调递增事件数，用 `rate/increase` 看速率。
- Gauge：当前状态，可能上下变化，例如队列长度、连接数。
- Timer：次数与耗时分布。
- Histogram：把样本落入 Bucket，可跨实例聚合估算分位数。

客户端直接计算 Summary Quantile 通常不易跨实例聚合；服务端 Histogram 更适合多实例 P95，但 Bucket 设计影响精度与成本。

### 标签基数

不能把 `userId/sessionId/requestId` 作为 Metric Label，否则时间序列爆炸。项目 Span/Metric 使用 Endpoint、Status、Model、Intent、Degraded 等受控标签；高基数标识放日志或审计库。

## 3. Prometheus 告警

告警应围绕用户影响和可执行动作，而不是“所有指标都告警”。项目包含：

- API 错误率/P95。
- Agent 成功率与规则违规。
- LLM Fallback 比例。
- Outbox 最老待处理时间。
- Hikari 连接池使用率。
- AI 建议转化、单位成功成本、疼痛/完成率回归，并设置最小样本门槛。

`for` 持续窗口减少瞬时尖峰误报；Severity 区分 Warning/Critical。生产还应配置抑制、分组、静默、值班路由和 Runbook。

**追问：为什么不用平均延迟？** 长尾会被平均值掩盖，用户体验通常由 P95/P99 决定；但分位数也要结合吞吐与错误率，低流量 P99 没有稳定意义。

## 4. OpenTelemetry、Tempo、Loki

OpenTelemetry 提供统一 Trace/Metrics/Logs 语义与 SDK。FitPilot 通过 Micrometer Tracing Bridge 导出 OTLP 到 Collector，再进入 Tempo；JSON Log 由 Promtail 采集到 Loki。

- Trace 展示 HTTP → Agent → LLM → Tool → RAG/Repository 的耗时链。
- Loki 以标签索引日志元数据，正文压缩保存；标签同样要避免高基数。
- Tempo 主要存 Trace，通过 Trace ID 关联日志和指标。

基础 Compose 默认关闭 OTLP Exporter，避免 Collector 未启动时持续报错；Observability Profile 才开启。

### Sampling

开发默认可全采样，生产全采样成本高。可使用概率采样、错误/慢请求 Tail Sampling、关键业务全采样。Tail Sampling 需要 Collector 观察完整 Trace，资源成本更高但更能保留异常样本。

## 5. SLI、SLO 与 Error Budget

- SLI：实际测量指标，例如成功率、P95、正确结果率。
- SLO：目标，例如 30 天可用性 99.9%。
- SLA：对外合同承诺，通常伴随赔偿。
- Error Budget：`1 - SLO` 允许的失败空间，用于平衡发布速度与可靠性。

FitPilot 已有指标和告警，但真实生产 SLO 仍是后续工作，不能把本机门禁阈值说成生产 SLO。

## 6. 测试金字塔与测试类型

- Unit Test：验证纯领域规则和小组件，快且定位清晰。
- Integration Test：验证 Spring、数据库、Redis、Kafka、ES 等真实协作。
- Contract Test：验证事件/API/外部 Provider 协议兼容。
- E2E：从浏览器到后端覆盖关键业务，最接近用户但慢且脆弱。
- Performance/Chaos：验证容量和故障语义，不替代功能正确性。

FitPilot 后端使用 JUnit 5、Mockito、Testcontainers、Awaitility；Web 使用 Vitest、RTL、MSW、Playwright。统一门禁要求零跳过。

## 7. Testcontainers

Testcontainers 在测试期间启动真实 PostgreSQL/pgvector、Redis、Kafka 和 Elasticsearch 容器，动态注入连接参数。

### 优势

- 验证真实 SQL 方言、扩展、索引、事务和中间件协议。
- 比共享测试环境隔离、可复现。
- 能执行 Flyway V1-V18，发现 H2 无法暴露的 PostgreSQL 兼容问题。

### 代价

- 启动慢、需要 Docker、资源占用高。
- 仍不等于真实生产拓扑、网络和数据规模。
- 测试等待异步结果应使用 Awaitility/轮询条件，不写固定长 Sleep。

**问：为什么不用 H2？** H2 无法准确覆盖 pgvector、PostgreSQL 部分索引、JSONB、锁语义和 SQL 方言；快但可能产生虚假信心。

## 8. JaCoCo 与覆盖率

项目总体行覆盖率门槛 60%，关键 Application/Domain 包 70%；当前功能基线实际为 84.40%。覆盖率说明代码被执行，不说明断言有效、边界完整或需求正确。

提高覆盖率应增加关键成功/失败行为测试，不能排除难测文件或只断言“没有抛异常”。Mutation Testing 可进一步检验测试能否杀死逻辑变异，但成本更高。

Maven Enforcer 禁止 `skipTests/skipITs/maven.test.skip`，Surefire/Failsafe 要求测试集非空，最终解析 XML 要求 Skipped=0，避免“绿色构建但测试没跑”。

## 9. 前端质量门禁

- ESLint：静态规则与潜在错误。
- TypeScript：编译期类型约束。
- Vitest + RTL：以用户行为和 DOM 结果验证组件。
- MSW：在网络边界 Mock HTTP，避免直接 Mock 内部实现。
- Playwright：真实 Chromium 覆盖登录、Token Refresh、Workout、Agent 确认和计划冲突。

E2E 应只覆盖最关键闭环和失败路径，避免把所有组合都放浏览器层。异步断言使用 `findBy/waitFor`，不要依赖脆弱时间。

## 10. Docker

### 原理

容器不是轻量虚拟机；它共享宿主机内核，通过 Namespace 隔离进程/网络/挂载等视图，通过 Cgroup 限制 CPU/内存，镜像由只读 Layer 组成并叠加可写层。

### FitPilot 落地

- Docker Compose 编排 App、Web、PostgreSQL、Redis、Kafka、Elasticsearch及可选可观测栈。
- 应用镜像以 UID 10001 非 Root 运行，支持只读根文件系统。
- 资源限制、日志轮转、Healthcheck 和 30 秒优雅停机。
- Secret 从环境注入，不打入镜像。

### 高频追问

**问：CMD 和 ENTRYPOINT 区别？** ENTRYPOINT 定义主要可执行程序，CMD 提供默认参数或默认命令，运行时更容易覆盖 CMD。

**问：为什么多阶段构建？** 构建环境与运行环境分离，减少最终镜像体积、编译工具和攻击面。

**问：容器内存超限会怎样？** Cgroup 限制触发 OOM Kill；JVM 要感知容器限制并合理设置 Heap/Direct Memory，否则只看 `-Xmx` 不够。

## 11. Kubernetes 基础对象

- Deployment：声明无状态 Pod 副本和滚动更新。
- Service：为 Pod 提供稳定虚拟地址与负载均衡。
- Ingress：HTTP 入口路由。
- ConfigMap/Secret：配置与敏感值注入；Secret 只是 Base64，仍需 RBAC/加密/KMS。
- Job：一次性任务，项目用于 Flyway Migration。
- HPA：根据 CPU 等指标调整副本。
- PDB：自愿驱逐期间保证最小可用副本。
- NetworkPolicy：限制 Pod 入站/出站。

## 12. Kubernetes 探针与优雅停机

- Startup Probe：慢启动期间保护 Liveness，不让应用反复重启。
- Liveness Probe：判断进程是否需重启，不应依赖容易波动的外部系统。
- Readiness Probe：判断是否接收流量，可以包含 DB/Redis 等必要依赖。

FitPilot 管理端口 9091；Startup/Liveness 使用 Liveness Group，Readiness 包含 DB 和 Redis。Pod 停止时先进入 NotReady，`preStop` 等待 5 秒，Spring Boot 再在 30 秒宽限期内优雅关闭。

项目业务设计允许 Redis 故障时缓存回源和限流降级，但当前 Readiness 包含 Redis，会在 Redis 故障时把 Pod 摘流。这两者存在策略张力：若希望 Redis 故障时继续核心业务，生产应使用自定义 Readiness，只把数据库等硬依赖作为摘流条件，将 Redis 健康单独告警；若数据库会被回源流量压垮，则保持摘流并明确容量策略。面试时应说明这是可用性与下游保护的取舍。

**追问：Readiness 失败会重启 Pod 吗？** 不会，只从 Service Endpoint 移除；Liveness 失败才触发重启。

## 13. Rolling Update、PDB 与 HPA

Production Overlay：2 副本，`maxUnavailable=0`、`maxSurge=1`，MinReady 10 秒。更新时先额外起新 Pod，Ready 后再下旧 Pod。

PDB `minAvailable=1` 只约束节点维护等自愿驱逐，不阻止应用自身滚动策略或节点故障。HPA 2-10、副本目标 CPU 70%；扩容速度还受启动时间、指标周期和下游容量限制。

**追问：HPA 扩容为何仍可能雪崩？** 新 Pod 启动需要时间，流量已超过下游 DB/Kafka/Redis 容量；CPU 也可能不是正确瓶颈指标。需结合队列长度、并发、预扩容和下游保护。

## 14. NetworkPolicy 与容器安全

项目设置：Non-root、禁提权、只读根文件系统、Drop All Capabilities、RuntimeDefault Seccomp、关闭 ServiceAccount Token 自动挂载；NetworkPolicy 只允许 Ingress/Web/Observability 等来源和必要端口。

NetworkPolicy 需要 CNI 支持，否则 YAML 存在也不生效。`0.0.0.0/0` Egress 虽限制端口但仍较宽，可演进为具体 CIDR、DNS Policy 或 Service Mesh Egress。

## 15. 数据库迁移与发布顺序

Migration Job 先执行 Flyway，成功后 Rollout App 和 Web。应用 Pod 设置 `FLYWAY_ENABLED=false`，避免多副本启动时同时迁移。迁移只允许向前兼容，回滚应用镜像而不是自动 Down Migration。

真实交付门禁还包括：精确 Kube Context、不可变镜像 Digest、Readiness、PDB/HPA/NetworkPolicy、Rollback/候选恢复、备份恢复和 JWT/Operations Token 轮换。

## 16. CI/CD 与供应链安全

### CI

- Java/Web 统一质量门禁。
- CycloneDX 生成 `target/bom.json`。
- Trivy 扫依赖 SBOM 和两个候选镜像的 High/Critical。
- Gitleaks 扫完整 Git 历史。
- 校验 Compose、Kustomize、Prometheus、Alertmanager。

### Release

- 只由成功 CI 的 `workflow_run` 触发。
- `select-revision` 比较 CI Head SHA 与最新 `origin/main`，拒绝过期 CI 覆盖 `main` 标签。
- 再次执行质量和镜像安全门禁。
- 发布 `linux/amd64`、`linux/arm64` GHCR OCI Index。
- 归档 Revision、Image Digest、SBOM 和 SLSA Provenance。

### 术语

- Tag 可变，Digest 是内容寻址且不可变；生产应按 Digest 部署。
- SBOM 是组件清单，不等于漏洞扫描，也不证明组件安全。
- Trivy 根据漏洞库匹配依赖/镜像，不会发现所有业务逻辑漏洞。
- Gitleaks 扫密钥模式，不替代 Secret Manager 和密钥轮换。
- Provenance 证明“由什么源码和 Workflow 构建”，不证明软件没有漏洞。

## 17. 备份、恢复与灾难恢复

- Backup 成功不等于可恢复，必须定期 Restore Drill。
- RPO：最多可接受丢失多少数据。
- RTO：故障后多久恢复服务。
- 数据库备份、Kafka 保留、对象存储和 Secret 恢复策略要分别设计。

项目已在历史 Kind 演练验证备份恢复脚本，但真实生产集群未执行 Delivery Gate，不能宣称已达到生产 RPO/RTO。

## 18. 高频追问

**问：Metrics、Logs、Traces 如何定位一次慢请求？** 告警从 Endpoint P95 发现异常，通过 Exemplars/时间窗口找 Trace，Trace 看哪一 Span 慢，再用 Trace ID 查 Loki 日志和数据库/中间件指标。

**问：为什么 Release 还要重新跑测试？** CI 与发布之间可能有过期结果、环境差异或供应链变化；Release 只接受最新 Revision，并重新验证候选镜像。

**问：为什么用 Digest 不用 Tag？** Tag 可以被覆盖，同名不一定同内容；Digest 绑定具体 Manifest，便于审计和回滚。

**问：Kubernetes 高可用是否只要多副本？** 不是。还需跨节点/可用区调度、PDB、探针、下游 HA、容量、备份、故障转移和流量入口保障。

## 19. 本章一段话总结

> FitPilot 用 Micrometer/OTel 将 HTTP、Agent、LLM、Tool、RAG 和中间件链路接入 Prometheus、Tempo、Loki 与 Grafana，并用低基数指标和最小样本告警控制噪声。质量门禁从单元、Testcontainers 集成到浏览器 E2E，强制零跳过和覆盖率。交付使用非 Root 容器、独立 Flyway Job、滚动更新、探针、PDB/HPA/NetworkPolicy，并以最新 Revision、Digest、SBOM 和 Provenance 建立供应链证据；真实生产门禁仍需真实环境执行。
