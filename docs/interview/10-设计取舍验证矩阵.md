# FitPilot 设计取舍验证矩阵

日期：2026-09-16。基于当前 `README.md`、`docs/architecture/v1-v6`、现有验收报告和源码入口整理。本文是实验方案，不是已完成实验或生产效果声明。执行每项实验前先固定目标场景、成功阈值、代码 SHA、数据集、配置、硬件、负载和观测窗口；保留原始报告与失败样本。不要只比较速度，还要比较故障边界与维护成本。

逐项执行步骤、分期与结果报告格式见[详细测试计划](../test-plans/设计取舍验证测试计划-2026-09-17.md)。

## 核心业务与数据

| 取舍 | 更简单的对照 | 验证方法与指标 | 保留条件 / 现有证据 |
|---|---|---|---|
| 模块化单体 + PostgreSQL，而非微服务/多数据库 | 同一单体内按功能分包，或不增加中间件 | 用 ArchUnit/依赖图检查跨模块边界和循环依赖；测新增训练功能需要修改的模块数、一次发布/回滚所需步骤、核心写链路事务数。只有独立扩容、故障隔离或发布节奏出现实测瓶颈，才评估拆服务。 | 单体是当前低成本基线；不必为了“证明微服务不如它”而新建微服务。 |
| 训练开始时保存计划快照 + 数据库状态/唯一约束 | Workout 每次引用当前计划；只在 Service 中检查 | 开始训练后修改原计划，核对历史动作与目标不变；并发开始、加组、完成、重试，检查最多一个 ACTIVE、组号不冲突、无半完成状态。指标是违反业务不变量的次数及事务冲突结果。 | 已有源码和集成测试可证明指定并发场景的正确性；真实使用频率仍需统计。 |
| 手机端本地恢复 + PostgreSQL 操作回执 | 仅前端内存/Redis 幂等键 | 真机或手机视口执行断网、刷新、关页、响应丢失、重复点击、多标签页、跨设备结束；核对“用户已确认组”与数据库组/本地队列逐条一致，记录恢复时间、冲突率、记录耗时和误操作。 | V19 本地测试覆盖多个故障场景；仍需真实用户使用与浏览器存储回收边界验证。 |

## 性能与异步可靠性

| 取舍 | 更简单的对照 | 验证方法与指标 | 保留条件 / 现有证据 |
|---|---|---|---|
| Kafka + Outbox/Inbox 处理派生任务 | 同事务同步更新；PostgreSQL 任务表 + worker | 同一业务数据与写入速率，比较 Workout 完成 P95/P99、数据库负载、事件积压年龄、恢复到追平的时间、部署/排障步骤。注入 Kafka 停机、发出后回写失败、重复消息、毒消息和消费者重启，核对 Workout 真源与投影。 | Outbox 故障正确性已有测试，Kafka 相对数据库任务表的吞吐/成本优势尚需对照；没有优势就保留简单方案。 |
| 领取 token、Inbox 和业务唯一约束 | 仅状态字段或仅消费者去重 | 两个 Relay 构造 A 超时、B 重领、A 晚成功/失败；发送成功但标记前宕机，重复投递；检查新领取状态不被旧回调覆盖、PR/分析/通知不重复。 | V20 有真实 PostgreSQL 的领取测试；语义仍是至少一次投递，不宣称严格顺序或 Exactly Once。 |
| Caffeine L1 + Redis L2 + 短 TTL | PostgreSQL 直读；只用 Redis | 在当前短 TTL 配置下，用相同数据量、冷热比例、读写比和两实例拓扑分别测试三种方案。记录 P95/P99、吞吐、数据库 QPS/CPU、Redis 流量、内存、旧值持续时间和 Redis 故障回源压力。 | 必须在满足展示陈旧度目标后，仍显著降低资源成本或改善用户延迟；历史单热点 10 秒压测不够。 |
| Redis 限流/通用幂等 + 数据库业务约束 | 网关限流；仅数据库唯一约束/回执 | 多实例突发请求、Redis 故障、键过期和同键不同载荷，测误放/误拒、核心写入是否重复、限流后的数据库保护效果与额外请求延迟。 | 数据库约束是最终正确性来源；Redis 层须证明对突发流量或用户体验有增益。 |

## 检索与 Agent

| 取舍 | 更简单的对照 | 验证方法与指标 | 保留条件 / 现有证据 |
|---|---|---|---|
| Parent-Child Chunk + BM25/pgvector 双路 + RRF/Rerank | 单层 Chunk + BM25；单层 Chunk + 向量 | 固定文档版本，训练/调参集与留出测试集分离；按术语、同义表达、长文、无答案、失效文档分类。比较 Recall@5、MRR、人工核对的“引用支持结论”比例、P95、索引更新/删除延迟和资源成本。更换真实 Embedding 后重建索引并重测。 | 仅当混合方案对关键分类有稳定净增益且延迟/成本可接受时保留 ES；默认本地哈希 Embedding 的结果不能外推到真实模型。 |
| 单 Agent、规则回退、只读工具与待确认写入 | 纯规则建议；LLM 直接生成文本但不执行工具 | 用相同用户事实和盲评样本比较建议可用性、正确工具选择、越权/危险提议、用户理解度、确认/拒绝原因、P95 与成功成本。对跨用户、过期计划、重放令牌、提示注入做故障测试，核对未确认零写入。 | 后端授权和确认的正确性可由故障测试证明；Agent 相对规则的业务收益必须靠真实模型与用户反馈证明。不得用“确认率”单独代表建议正确。 |
| PostgreSQL 会话真源 + Redis 近期缓存 | 只用 PostgreSQL 会话 | 多设备交替、Redis 清空/故障、会话删除与待确认恢复；比较读取 P95、数据库 QPS、恢复完整率和多实例一致性。 | 跨设备/故障恢复由功能测试证明；只有会话读热点确实减轻数据库压力时才保留 Redis 会话缓存。 |
| 主备模型路由、重试、熔断、规则降级 | 单模型 + 明确失败提示 | 固定真实模型/Prompt/数据集，注入 429、超时、坏 Schema、主服务不可用，比较可完成任务比例、错误建议率、P95/P99、费用、降级后用户是否仍能完成任务；验证共享 Deadline 不被多次重试突破。 | 真实模型评测和外发数据/预算审批后才能作质量结论；Mock 链路只证明协议和容错实现。 |

## 实施顺序与报告格式

1. 优先完成真实用户记录体验、离线恢复和核心写入故障实验。这些直接决定产品主线是否有用。
2. 其次做缓存与 Kafka 的三方案同条件对照。若复杂方案不带来可测收益，应缩减复杂度。
3. 最后做真实 Embedding/LLM 的盲评和成本实验，决定双检索、模型路由及 Agent 的长期保留范围。

每项只需一页报告：**假设、简单方案、当前方案、预先确定的门槛、实验环境与 SHA、原始数据、失败案例、增加的运行成本、结论和边界**。正确性测试、性能对照、真实用户价值是三种不同证据；一项通过不能替代另两项。已有资料入口：[V19 离线恢复](../release/workout-auto-recovery.md)、[V20 Outbox 领取](../release/outbox-claim-ownership.md)、[短 TTL 缓存](../release/short-ttl-cache-consistency.md)、[V18 功能验收](../release/v18-functional-validation.md)、[AI 产品指标](../release/ai-product-value-metrics-validation.md)。
