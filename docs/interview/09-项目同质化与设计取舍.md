# FitPilot 同质化与设计取舍评估

评估日期：2026-09-16。代码基线：`c216211`。本次核对当前源码、README 和既有验证报告；未运行新测试、真实模型评测或用户实验。市场对照基于 [Hevy 功能页](https://www.hevyapp.com/features/) 与 [Fitbod 功能说明](https://help.fitbod.me/hc/en-us/sections/360001078993-How-Fitbod-Works)，只比较公开功能，不推断其内部架构。

## 结论

产品功能与成熟健身应用明显重合，不能以“训练记录 + 智能计划”作为独有卖点。项目作为 Java 后端与 AI 应用工程作品有可讲的真实故障边界，但部分中间件和交付设施先于用户规模及业务效果证据。适合定位为“可信训练记录驱动的可确认 AI 调整原型”，不宜宣称已验证市场差异化或生产规模必要性。

| 问题 | 当前证据 | 判断与面试边界 |
|---|---|---|
| 同质化 | Hevy 已覆盖计划、逐组记录、历史、PR 和进度；Fitbod 用训练历史生成动态建议。本项目也覆盖这些功能。 | 重合高。差异化假设是训练记录恢复、调整证据与确认链路；需要真实用户验证体验和收益。 |
| 为了做而做 | 逐组快速记录、离线恢复、数据库回执对应健身房弱网和误操作场景；Outbox 的超时重领曾有可复现晚回调风险。 | 这些有具体失败场景，可讲清楚。MCP、复杂交付门禁、全套可观测等更偏工程展示，目前缺少使用频次或运营约束证明优先级。 |
| 过度设计 | 单体内同时使用 Kafka + Outbox/Inbox、Caffeine + Redis、pgvector + Elasticsearch、规则/主备模型路由及 Kubernetes 脚本。 | 对当前未证实的用户量，这套部署与维护成本偏高。模块化单体、训练快照、数据库唯一约束、确认前重校验应保留；其余组件要按压测、检索评测或故障恢复目标证明增益。 |
| 选型可解释性 | 完成训练后 PR/分析/通知可异步派生；RAG 有关键词和语义两路召回；展示缓存允许短暂旧值。 | 可以解释“为什么这样实现”和失败恢复，尚不足以证明“为什么一定要 Kafka/ES/L1+L2”。面试应主动给出更简单的备选及升级阈值。 |

## 优先讲清的四个选型

1. **PostgreSQL + 模块化单体**：训练状态、组次、计划版本和所有权需要事务与约束；模块化单体降低跨服务事务和部署复杂度。训练快照及数据库回执比增加服务数量更贴近业务。依据：`WorkoutService`、`RecoverableSetService`、V19 验证报告。
2. **Kafka + Outbox/Inbox**：当前作用是让训练完成先提交，PR、分析和通知随后追平；Outbox 处理“数据库成功、消息失败”，Inbox/唯一约束处理重复投递。若只有单实例和少量派生任务，数据库任务表或同步更新更简单；需以积压、隔离、扩展或吞吐需求证明 Kafka 价值。V20 领取 token 只保护状态回写，不保证 Exactly Once。依据：`WorkoutService.complete`、`OutboxRelay`、Outbox 领取保护报告。
3. **Caffeine + Redis**：热点读压测说明有读路径优化空间，但短 TTL 配置后没有同条件新容量数据。L1 跨实例旧值由短 TTL 收敛，关键业务判断仍读数据库。若无明确多实例热点和数据库压力，可先只用数据库或单层 Redis。依据：短 TTL 缓存策略、V1 性能报告。
4. **pgvector + Elasticsearch + Agent**：双路召回与受控确认是可研究的工程方案，但默认 Embedding 为本地哈希，CI 使用 Mock LLM；目前没有真实模型质量、检索收益、真实用户训练改善的证据。应先用固定数据集比较 BM25、向量、混合检索与规则建议的质量、延迟和成本，再决定是否长期保留双引擎与模型路由。依据：`application.yml`、`HybridRetrievalService`、V18 功能报告及 AI 产品价值指标报告。

## 面试表述

“这个项目的训练记录、计划和进度功能与现有健身产品重合，我不把它包装成产品创新。我的重点是训练数据可靠写入后，怎样让 AI 读取真实数据、给出可解释草案，并由后端校验和用户确认。为了验证后端故障边界，我实现了 Outbox、幂等回执和降级路径；但 Kafka、双检索和二级缓存的规模收益尚未被真实用户与同条件对照验证。下一步先做小规模真实试用、写链路压测与真实模型离线评测，再决定哪些组件值得保留或简化。”

## 下一步证据

- 让少量真实用户完成训练记录和调整闭环，观察记录耗时、恢复成功率、建议接受率与拒绝原因；不要把测试样本的指标当作用户收益。
- 同数据同机器比较数据库/单层缓存/二级缓存，以及同步派生/数据库任务/Kafka 链路的延迟、吞吐、故障恢复与运维成本。
- 固定脱敏问题集，比较规则、BM25、向量与混合检索，记录引用是否支持结论、人工评价、P95 与单次成功成本。

资料边界：本机历史性能和测试仅证明其对应 revision/环境；当前 HEAD 不自动继承远端发布或生产证据。真实 Production Delivery Gate 为 `SKIPPED`。

## 如何证明设计有用（2026-09-16 补充）

先写一张实验卡：**用户/故障场景 → 最简单可行方案 → 当前设计 → 事先确定的成功标准 → 同条件原始数据 → 增益和新增成本 → 保留或简化决定**。固定代码 revision、数据量、硬件、负载、测试时长与测量脚本；保留失败样本。只证明实际测过的边界。

| 优先级 | 待验证的假设 | 对照与测量 | 能支持的结论 |
|---|---|---|---|
| 1 | 快速记组、离线恢复确实减少训练中断和记录丢失 | 请少量目标用户在手机上完成真实训练；同一任务比较手动输入与历史预填，记录每组操作耗时、误触/改错、未同步组、恢复成功率和主观负担。另用断网、刷新、响应丢失、跨设备冲突做故障演练。 | 小样本可证明可用性问题及改进方向，不能声称市场留存或训练成效提升。 |
| 2 | 数据库回执与 Outbox 的额外复杂度解决了可观察的写入故障 | 对照无数据库回执的重试、同步派生或数据库任务表；注入提交后响应丢失、Kafka 不可用、消费者重复、Relay 超时重领，核对训练事实、重复组数、派生追平时间及故障期间核心写请求结果。 | 可证明特定故障下的正确性与恢复能力；Kafka 是否优于数据库任务仍需吞吐和维护成本数据。 |
| 3 | 两级缓存的收益大于陈旧数据与维护成本 | 在同一 revision/数据集、读写比和多实例拓扑下，对照数据库直读、Redis 单层与 L1+L2；测 P95/P99、数据库 CPU/QPS、缓存命中率、跨实例旧值窗口、Redis 故障恢复。 | 若收益不明显，优先保留简单方案。历史 V1 热点读压测不能替代短 TTL 后的对照。 |
| 4 | 双路 RAG 与 Agent 比简单规则/单路检索产生更好的建议 | 固定脱敏问题集和人工标注，分别运行规则、BM25、向量、混合检索与真实模型；测 Recall@K、MRR、引用是否支持结论、危险建议拦截、人工偏好、P95、单次成功成本。评测集与调参集分开。 | Mock LLM、默认本地哈希 Embedding 和受控指标样本只证明链路可运行，不证明真实建议质量。 |

建议先完成第 1、2 项：它们最接近产品主线，也最容易取得可复现证据。第 3、4 项的结果再决定 Redis L1、Kafka、Elasticsearch 和模型路由是否值得持续维护。实验报告至少附原始数据、失败案例、配置、脚本、revision 和环境；预先写明目标，避免看到结果后修改成功标准。

各项架构取舍的对照方案和实验指标见[设计取舍验证矩阵](10-设计取舍验证矩阵.md)。
