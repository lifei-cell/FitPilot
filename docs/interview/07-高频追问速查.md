# FitPilot 高频追问速查

> 目标：每题先用一句话给结论，再补项目落地与边界。不要一上来背完整定义。

## 一、架构与领域

### 1. 为什么是模块化单体，不是微服务？

当前没有独立扩缩容、团队自治或故障隔离的真实瓶颈，单体能保持本地事务和低运维成本；通过包边界与 Kafka 投影解耦，等证据出现后再拆。

### 2. 模块化单体和普通单体的本质差异？

是否有明确业务边界和受控依赖。FitPilot 按领域包拆分，Controller/Service 不应跨模块直接访问 Mapper，派生能力用事件解耦。

### 3. 为什么 TrainingPlan 和 Workout 要分开？

计划是可变意图，Workout 是历史事实；开始训练时复制快照，避免计划修改后历史、PR 和 Analytics 口径漂移。

### 4. 冗余快照违反数据库范式吗？

它是有业务语义的反范式设计，类似订单商品快照；用存储换历史一致性与审计性，不是无控制重复。

### 5. 如何保证一个用户只有一个 ACTIVE 计划？

应用激活时归档旧计划，数据库用 `UNIQUE(user_id) WHERE status='ACTIVE'` 最终兜底，并发下数据库约束才是最后防线。

## 二、Spring 与安全

### 6. `@Transactional` 为什么可能失效？

Spring 事务依赖代理；同类自调用、非 Spring 对象、异常被吞、检查异常未配置、新线程等都会绕过或脱离事务。

### 7. 为什么不把大流程全放一个事务？

大事务持锁久、占连接、冲突和回滚成本高；Workout 事务只提交事实与 Outbox，PR/Analytics/通知异步处理。

### 8. JWT 无状态，为何还要 Refresh Token？

短期 Access Token 便于验签和扩展，长期 Refresh Token 负责续期且可撤销、可轮换；两者分离降低 Access Token 泄漏窗口。

### 9. JWT 能加密用户数据吗？

普通 JWS JWT 只签名不加密，Payload 可被读取，不能放密码或隐私。

### 10. Refresh Token 为什么存哈希？

Redis 泄漏时存储值不能直接换会话；用户提交 Token 后再做 SHA-256 匹配。高熵 Token 不需要像低熵密码那样使用慢哈希。

### 11. 如何平滑轮换 JWT 密钥？

先部署“新密钥签发、双密钥验签”，等待旧 Token 兼容窗口，再撤销 Previous Secret；项目有双密钥配置和轮换演练脚本。

### 12. 如何防 IDOR？

身份只来自 JWT，Repository 查询直接带 `userId + resourceId`，未命中统一返回 Not Found；不能先按 ID 查再信任客户端 User ID。

## 三、PostgreSQL

### 13. PostgreSQL MVCC 是什么？

更新生成新行版本，事务快照决定可见性，读写多数情况下不互阻；旧版本由 VACUUM 回收，但同一行更新和 DDL 仍会锁竞争。

### 14. 为什么不用 Serializable 解决所有并发？

隔离越高冲突和重试成本越大；项目用短事务、局部行锁、乐观锁和唯一约束解决具体不变量。

### 15. Set 编号并发如何处理？

对单个 `workout_exercise` 行执行 `FOR UPDATE` 后计算序号，唯一约束 `(workout_exercise_id,set_number)` 再兜底。

### 16. 乐观锁和悲观锁如何选？

读多写少、冲突低用 Version 乐观锁；必须短时串行的临界区用行锁。计划编辑用乐观锁，Set 编号用悲观锁。

### 17. 部分索引是什么？

只索引满足谓词的行，例如只索引待处理 Outbox 或 ACTIVE 计划，索引更小、维护成本更低；查询条件必须能匹配谓词。

### 18. 怎么判断索引真的有用？

看 `EXPLAIN (ANALYZE, BUFFERS)` 的实际行数、耗时、循环、块命中和回表，不只看是否出现 Index Scan。

### 19. Flyway 迁移为什么不能改旧文件？

共享环境已记录校验和，修改会造成环境历史不可追溯；应该新增向前迁移修复。

## 四、Redis 与缓存

### 20. Redis 为什么快？

内存访问、命令主线程串行减少锁竞争、高效数据结构和 IO 模型共同作用；复杂 O(N) 命令仍会阻塞。

### 21. L1 + L2 有什么价值和问题？

L1 消除网络延迟，L2 跨实例共享并减 DB 压力；问题是多实例 L1 失效不一致、序列化和双层运维复杂度。

### 22. 穿透、击穿、雪崩分别怎么处理？

穿透用空值缓存；击穿用重建锁、二次检查和有限等待；雪崩用 TTL 抖动、容量保护和故障回源。

### 23. Cache Aside 能强一致吗？

不能。提交后删缓存仍有删除失败和其他实例 L1 陈旧窗口；通过 After Commit、TTL、重试/失效广播和数据库真源收敛。

### 24. 分布式锁为什么用 Lua 解锁？

必须原子执行“Value 是我的 Token 才删除”，否则旧持有者可能误删新持有者的锁。

### 25. 这个 Redis 锁有哪些漏洞？

业务超过 TTL、主从切换丢锁和多实例时钟/网络都可能造成并发；因此只用于缓存重建，不作为核心业务正确性依据。

### 26. 为什么限流用令牌桶？

允许一定突发并控制长期速率，适合 API；Lua 原子计算补充与扣减，Redis 故障时降级本地桶但不再保证全局精确。

### 27. Idempotency-Key 与数据库唯一约束谁更重要？

两者层次不同：Key 改善请求重试体验并可回放响应，数据库约束保证最终业务不变量；Redis Fail-open 时后者仍必须有效。

### 28. 项目 Idempotency Filter 还能怎么增强？

把请求 Body Hash 与 Key 一起保存，拒绝同 Key 不同 Payload；限制响应大小；长任务续租；对核心接口增加数据库幂等记录。

## 五、Kafka 与事件

### 29. 为什么不用数据库更新后直接发 Kafka？

两步之间宕机会丢消息；Outbox 将业务事实和待发送事件放同一数据库事务，Relay 后续发送。

### 30. 为什么 Outbox 不是 Exactly Once？

Kafka 发送成功后、标记 SENT 前宕机会重发；项目接受重复，用 Inbox 和业务唯一约束消副作用。

### 31. `acks=all + enable.idempotence=true` 是否 Exactly Once？

只提升 Producer 到 Kafka 的可靠性和分区内重试去重，不能覆盖数据库写、Relay 状态和消费者副作用。

### 32. Kafka 如何保证顺序？

只保证单 Partition 顺序；同一聚合使用固定 Key。跨 Partition 无全局顺序，扩分区也要评估 Key 映射变化。

### 33. Offset 提交早晚有什么风险？

业务前提交可能丢处理，业务后提交可能重复；项目业务事务成功后确认 Offset，并让消费者幂等。

### 34. Consumer Rebalance 会发生什么？

Partition 重新分配，未提交 Offset 的消息可能被新消费者重放；长处理还可能超 `max.poll.interval`，因此要控制处理时长和幂等。

### 35. 消息积压怎么排查？

比较生产/消费速率、Partition、Consumer 数、单条耗时、DB 延迟、毒消息和 Rebalance；先找瓶颈再扩容，消费者并发不超过 Partition 有效并发。

### 36. DLT 后消息顺序怎么办？

坏消息被隔离后后续消息可能越过它；若业务要求严格顺序，需要暂停该 Key/Partition、修复后按序回放，而不是简单继续。

## 六、RAG

### 37. BM25 比 TF-IDF 改进在哪里？

加入词频饱和与文档长度归一化，避免一个词重复很多次或长文档天然得分过高。

### 38. 为什么向量检索还需要 BM25？

向量擅长语义，BM25 擅长精确术语、编号和专有名词；健身知识两类需求同时存在。

### 39. HNSW 原理是什么？

构建多层近邻图，高层长跳、底层精搜，以近似召回换低延迟；`m/ef_construction/ef_search` 在资源、延迟和召回间权衡。

### 40. RRF 为什么不用原始分数？

BM25 与 Cosine 分数尺度不同，RRF 只融合排名，减少归一化和模型变化带来的校准问题。

### 41. Parent-Child Chunk 解决什么？

Child 让检索更精确，Parent 保留完整回答语境；命中 Child 后回填 Parent，兼顾召回和上下文。

### 42. ES 和 PostgreSQL 数据不一致怎么办？

PostgreSQL 是真源，索引失败记录状态并后台重试；删除先让 PG Chunk 不可检索，再重试 ES；查询双侧过滤生命周期。

### 43. 如何证明 RAG 变好了？

冻结数据集比较 Recall@5、MRR、NDCG、Context Precision/Recall 和 Citation Validity，并分知识类别看回归；生成答案质量需单独评测。

### 44. 用户负反馈能直接调排序吗？

不能，容易被恶意或噪声污染；项目先人工审核并补正确来源，再进入版本化动态评测集。

## 七、Agent 与 LLM

### 45. 为什么不用 Multi-Agent？

单 Workflow 已覆盖业务，Multi-Agent 会增加路由、状态、循环、成本和排障复杂度；没有可量化收益不引入。

### 46. 如何防止模型越权调用 Tool？

JWT 提供身份，Tool 不接受 User ID，服务端白名单、强类型输入、Owner 查询、领域校验、Guardrail 和确认共同约束。

### 47. Prompt Injection 能完全防住吗？

不能；要用不可信数据隔离、最小权限 Tool、结构化校验、后端身份、确认、Citation、脱敏和对抗评测降低影响。

### 48. 为什么模型失败要回退 Rule Workflow？

保留安全的基础能力并避免外部 Provider 成为单点；降级只降低智能程度，不放宽权限和写入规则。

### 49. 哪些错误应该重试？

429、502/503/504、网络等瞬时错误可有界重试；Schema、安全、权限和确定性业务错误不重试，避免放大流量与费用。

### 50. 熔断、限流、降级有什么区别？

限流控制进入量；熔断在依赖持续失败时快速拒绝；降级提供较弱替代结果。三者解决不同阶段的问题。

### 51. 为什么确认时重新校验？

提议到确认间状态可能变化，重新核对 Owner、Token、过期、源计划 ID/Version 和领域规则，避免 TOCTOU。

### 52. 怎么控制 LLM 成本？

按任务路由模型、限制 Context、检索必要事实、限制并发/预算、记录 Token/费用、失败有界重试，并看单位成功成本而不是只看总成本。

### 53. MCP 是否自动解决安全问题？

不会。MCP 只标准化 Tool/Resource 发现与调用，认证、授权、参数校验、审计和确认仍由业务系统实现。

## 八、可观测与交付

### 54. Metrics、Logs、Traces 各自适合什么？

Metrics 看趋势和告警，Logs 看离散详情，Traces 看一次请求跨组件的因果与耗时；通过 Trace ID 和时间窗口关联。

### 55. 为什么不能用 User ID 做 Prometheus Label？

会造成高基数时间序列爆炸，增加内存、存储和查询成本；高基数标识放日志或审计库。

### 56. Readiness 和 Liveness 有什么区别？

Readiness 失败停止接流量但不重启；Liveness 失败触发重启；Startup 保护慢启动阶段不被 Liveness 杀死。

### 57. HPA 为什么不等于自动高可用？

扩容有延迟，CPU 未必是瓶颈，下游数据库也可能先饱和；还需副本分布、PDB、探针、容量和下游 HA。

### 58. Tag 和 Digest 有什么区别？

Tag 可覆盖，Digest 由内容计算且不可变；生产按 Digest 部署才能精确审计和回滚。

### 59. SBOM、Trivy、Provenance 分别证明什么？

SBOM 列组件；Trivy 用漏洞库匹配已知风险；Provenance 证明构建来源和 Workflow。三者都不证明业务逻辑绝对安全。

### 60. 为什么项目还不能说“已生产上线”？

远端 CI/Release/GHCR 和历史 Kind 演练已通过，但真实 Kubernetes Production Delivery Gate 未执行，状态是 `SKIPPED`。

## 九、面试官让你改进项目时

建议按优先级回答：

1. 增加 ArchUnit/模块边界自动测试，防模块化单体腐化。
2. 在真实生产环境执行 Digest 绑定的 Migration/Rollout/Rollback/Restore/Secret Rotation。
3. 建立真实 SLI/SLO、Error Budget 和多实例容量/故障演练。
4. 给 Idempotency-Key 增加 Request Body Hash 与数据库级核心幂等记录。
5. 为 L1 缓存增加跨实例失效通知，按业务一致性分级。
6. LLM Gateway 增加舱壁隔离、全局并发/预算控制和更完整半开熔断。
7. 用随机对照而不是简单前后对比验证训练调整的因果收益。
8. 当 Outbox 轮询成为明确瓶颈后，再评估 Debezium CDC。

## 十、容易说错的表述

| 不要说 | 正确说法 |
|---|---|
| Kafka 保证消息不丢不重 | 通过 Outbox 避免静默丢失，允许重复并由 Inbox/唯一约束幂等 |
| 实现 Exactly Once | 实现 At-least-once + 幂等消费 + 最终一致性 |
| Redis 锁保证业务强一致 | 锁只抑制缓存重建；核心正确性依赖数据库约束 |
| 缓存和数据库强一致 | Cache Aside 在可控窗口内最终收敛 |
| 稳定支撑 1000 QPS | 本机热点 GET 场景达到 998.83 req/s，但有 6 次 Dropped |
| RAG 杜绝幻觉 | RAG、Citation、校验和评测降低幻觉并提高可追溯性 |
| Agent 能自主安全写库 | 模型只提议，后端授权、校验、确认后写入 |
| 指标证明 AI 提升训练效果 | 受控测试证明聚合正确，线上前后对比仍是观察性证据 |
| 已生产上线 | CI/GHCR 已发布，历史 Kind 已演练，真实生产门禁仍 SKIPPED |
