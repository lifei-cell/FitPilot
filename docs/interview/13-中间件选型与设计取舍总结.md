# FitPilot 中间件选型与设计取舍总结

## 1. 总体设计：从业务约束出发

FitPilot 的主线是：**按计划开始训练 → 可靠记录每一组 → 完成训练 → 查看 PR 和统计 → 用户决定是否采纳 AI 调整建议**。

架构采用模块化单体。PostgreSQL 保存业务事实；缓存加速展示；异步任务生成派生结果；检索为知识回答提供材料。模型只能提议，后端负责身份、权限、规则校验、确认和持久化。

> [!important] 面试表达原则
> 先说业务问题，再说更简单的方案，最后说明当前方案增加了什么能力、付出了什么代价。实现可用、局部性能收益、生产必要性是三种不同结论。

本文把数据库、缓存、消息和检索组件作为核心中间件讨论；Caffeine 属于进程内缓存库，Micrometer、Flyway、MyBatis 等属于配套工具，Docker/Kubernetes 属于交付基础设施，不能都笼统叫成“分布式中间件”。

## 2. 选型总览

| 组件 | 项目中的职责 | 更简单或可替代的方案 | 主要代价 | 当前证据 |
|---|---|---|---|---|
| PostgreSQL | 训练事实、事务、约束、任务/回执、会话和知识真源 | 其他关系数据库，如 MySQL | SQL、索引、锁和连接资源需要治理 | 真实数据库集成测试；没有与 MySQL 做性能对照 |
| Redis | 共享缓存、限流、短期幂等响应、会话热数据等 | PG 直读、进程内缓存/限流 | 网络和序列化成本；故障降级；失效一致性 | 有缓存局部对照及既有降级测试 |
| Caffeine | 应用实例内的 L1 热点缓存 | 只用 Redis；小规模时只用本地缓存 | 多实例各持一份旧值，占用 JVM 内存 | 热命中收益已测，两个对象模拟独立 L1 |
| Kafka | 分发训练完成、PR 等事件 | 同事务同步派生、PG 任务 worker | Broker、消费位点、重试与回放运维 | 有事件正确性测试和局部三方案对照 |
| Elasticsearch | BM25 关键词候选与可重建索引 | 小语料下可评估 PG 全文检索；或单独向量检索 | 新增集群及双存储同步、删除传播 | 与向量/混合已做诊断对照；未测 PG 全文检索 |
| pgvector | 同库保存向量并执行向量检索 | 先用 BM25；规模变化后评估专用向量库 | 索引资源与业务数据库共享；效果依赖 Embedding | 真实 pgvector 链路，默认哈希向量不代表语义效果 |
| Prometheus / Grafana | 指标、趋势、面板与告警展示 | Actuator + 结构化日志 | 存储、标签基数和告警维护 | 有配置和指标；未证明生产 SLO 或定位效率提升 |
| OpenTelemetry / Tempo / Loki | 链路采集、Trace 和日志关联 | 结构化日志 + Request ID | 采集、采样、存储和运维成本 | 有集成配置；完整收益需故障定位对照 |

## 3. PostgreSQL：把业务不变量放在数据库边界内

### 解决什么问题

训练状态、动作快照、组记录、离线回执必须可靠保存。Workout 完成与 Outbox 事件需要一起提交；离线加组与成功回执也需要一起提交。私有资源查询包含用户归属条件。

### 为什么采用当前设计

PostgreSQL 的关系模型、事务、外键、唯一约束和行锁适合这些关联业务；项目还使用部分唯一索引、JSONB、`SKIP LOCKED` 和 pgvector，使业务、任务及向量数据保持在同一数据库体系中。

这说明 PostgreSQL 与当前实现匹配，不能推导出“MySQL 做不了训练系统”或“PostgreSQL 性能一定更好”。本项目没有做两种数据库的同条件对照。

### 事务、行锁、唯一约束的分工

| 机制 | 本项目的作用 | 单独使用的不足 |
|---|---|---|
| 事务 | 训练完成与 Outbox、组与回执一起成功或回滚 | 默认 READ COMMITTED 下，普通查询仍可能同时通过状态检查 |
| 行锁 | 同一 Workout 的写操作先锁父行，再检查状态、分配序号和修改 | 所有相关入口要遵循协议；同一训练内写入会等待，锁不自动验证业务 |
| 唯一约束 | 兜住动作序号、组号、回执键和进行中训练数量 | 不能表达“训练结束后禁止新增动作”，也不能负责重放原成功响应 |

已有训练统一走 owner 条件的 `SELECT ... FOR UPDATE`；新建训练尚无父行，使用用户行锁配合进行中训练的部分唯一索引。锁随事务提交或回滚释放。修改同一训练使用数据库锁，因此不同应用实例也能遵循同一协议。

**面试短答：** 我把正确性放在数据库事务和约束内，行锁串行化同一训练的检查与修改。缓存和消息系统可以故障，但不能成为训练事实唯一的保存位置。代价是同一训练的写操作会互相等待，需要控制事务范围并测量锁等待。

## 4. Redis：共享加速与流量治理，按职责选择故障策略

Redis 的用途要分开解释，不能只回答“提高性能”。

| 用途 | 当前机制 | 替代方案与边界 |
|---|---|---|
| 展示缓存 | Cache Aside、TTL 抖动、空值缓存、重建锁 | 低负载直读 PG 可能足够；冷回源有额外成本 |
| 限流 | Lua Token Bucket；故障时使用进程内桶 | 进程内桶只能约束当前实例，多实例总放行量可能增加 |
| 通用请求幂等 | 短期占位与成功响应回放 | Redis 过期/清空后不能独立保证永久业务幂等；训练仍靠数据库键、约束与回执 |
| Agent 最近消息 | PG 保存消息事实，Redis 缓存近期内容 | 可以只读 PG；共享缓存收益应根据会话读压力验证 |
| 缓存重建互斥 | 带 token 的锁，Lua 比较后删除 | 只控制重建竞争；不能替代训练事务和业务行锁 |

**代价：** 增加网络、序列化、数据失效与故障恢复路径；不是访问 Redis 就一定比数据库快。Redis 故障时缓存回源、限流降级只是保持可用的策略，数据库回源峰值和全局限流语义会变化。

**面试短答：** 我把 Redis 用在可重建数据和流量治理上。训练幂等的最终依据在数据库，Redis 主要减少重复请求和热点读取成本。故障时能降级不代表无代价，还要关注回源压力与多实例限流放宽。

## 5. Caffeine + Redis：为高复用热点支付一致性成本

### 简单方案与当前方案

- PG 直读：没有缓存失效协议，简单索引查询可能已经很快。
- Redis 单层：多个实例共享数据，减少重复数据库读取，每次仍有网络访问。
- 两级缓存：L1 热命中省掉 Redis 网络请求；L1 未命中再使用共享 L2。
- 仅 Caffeine：单实例、小热点且允许陈旧时可以考虑；多个实例分别重建，无法共享 L2 结果。

### 当前一致性选择

展示默认 L1 写入后 5 秒过期，L2 为 30 秒加最多 5 秒抖动；提交后删除当前实例 L1 和共享 L2。其他实例的 L1 靠过期收敛；关键业务状态直接读数据库。

> [!warning] 不要把“5 秒 TTL”说成全局强保证
> L2 删除失败或并发旧读回填可能让 L1 再加载旧数据。既有文档给出的自然过期窗口，是从最后一次旧值写入 L2 起、无后续旧回填时约 40 秒；不是从业务提交起算的严格时限。当前实验约 5.05 秒收敛只覆盖正常删除 L2 的特定场景。

### 本地对照结论

相同 1000 行表、同一 SQL，每轮 600 请求，3 轮轮换顺序：

| 场景 | PG 直读 P95 | Redis 单层 P95 | 两级缓存 P95 |
|---|---|---|---|
| 20 个预热热键 | 0.55–0.67 ms | 0.56–0.91 ms | 0.0014–0.0030 ms |
| 600 个不同冷键 | 0.55–0.58 ms | 2.89–3.56 ms | 2.90–3.07 ms |

热场景 PG 每轮查询 600 次，两个缓存方案均为 0 次 loader 回源；冷场景均为 600 次。冷路径的 Redis 访问、重建锁和回填使其更慢。

这是单 JVM 内顺序服务调用，两个独立 L1 对象模拟实例，不是 HTTP 压测。微秒级 L1 时延不能当作全系统响应时间；本次也未单独比较“仅 Caffeine”。

**面试短答：** 两级缓存的理由是热数据复用和减少网络访问。实验支持热 L1 的局部收益，也显示冷缓存更慢。我会根据真实命中率和数据库压力决定保留范围，并把展示陈旧与业务正确性分开处理。

## 6. Kafka：先论证异步，再论证 Broker

### 为什么需要异步

完成训练是主操作，PR、Analytics、通知是派生处理。同步执行时，用户等待全部处理，派生写失败也会回滚训练完成。异步允许训练事实先可靠落库，派生结果稍后收敛。

### 三种方案

| 方案 | 适用情况 | 增加的成本 |
|---|---|---|
| 同事务同步派生 | 数据少、计算轻、需要成功返回时结果已提交 | 事务长，派生失败影响主操作 |
| PG 任务表 + worker | 希望可靠异步，任务和消费者规模不大 | 领取、租期、重试、死信、清理及数据库轮询负载 |
| Outbox + Kafka + Inbox | 需要多个消费组独立推进、分发与按需回放 | Broker、消费位点、分区及排障流程，还要维护 Outbox/Inbox |

### 当前实现的职责分离

`Workout + Outbox 同事务 → Relay → Kafka → PR/Analytics → PR 事件 → 通知`。

- Outbox 解决业务事实与待发事件原子落库；不是 Kafka 自动让数据库双写原子化。
- `SKIP LOCKED` 让并发领取者跳过已锁行；领取 token 限制旧执行者晚返回时的数据库状态回写。
- token 不会撤销已发出的消息，也不是单调递增 fencing 序号。
- Inbox 与业务唯一约束处理重复投递；语义是至少一次投递与幂等业务效果，不宣称 Exactly Once。
- 不宣称事件严格按生成顺序发布；Kafka 分区内顺序也不能自动修复 Relay 已产生的乱序。

### 本地对照结论

每轮串行完成 20 个训练，异步组在所有请求提交后再启动派生；真实 PostgreSQL/Kafka，3 轮：

- 同事务组完成请求 P95：28.12–47.32 ms。
- PG worker 接受请求 P95：6.61–10.71 ms；批次追平约 533–609 ms。
- Kafka 分发组接受请求 P95：7.57–9.21 ms；批次追平约 686–803 ms。

异步组接受阶段都只写 Workout + Outbox，差异不能归功于 Kafka。当前实验 PG 追平更快，同步组接受到全部完成的总耗时也更短；“更早返回”不等于总工作更少。

同步组为了共用业务代码仍保留 Outbox/Inbox，不代表极简 CRUD 的最佳性能；PG 是测试 worker，Kafka 是单个实验消费者，未比较线上多消费组吞吐。20 样本的 P95/P99 很粗糙，只用于这个局部批次。

**面试短答：** 我用异步隔离派生处理，用 Kafka 表达独立订阅和回放能力；可靠性由 Outbox、Inbox 和数据库约束共同提供。本地对照没有证明 Kafka 比 PG worker 更快，当前规模下 PG worker 也是合理简化方案。

## 7. Elasticsearch 与 pgvector：两种候选来源，不能预设混合更准

### Elasticsearch：词项检索与可重建索引

ES 在项目中提供 BM25 候选，适合训练术语、动作名等词项匹配。知识文档、Chunk、版本和治理状态以 PG 为真源，ES 可以重建；索引失败有状态和重试，查询可降级到向量通道。

替代方案可以是先用 BM25 单路，或在更小需求下评估 PG 全文检索。PG 全文检索在本项目尚未进行实现与对照，不能说已验证可等价替换 ES。

代价是新增一个服务及索引同步、删除传播和故障排查。删除/撤销文档时需要处理 PG 与 ES 状态传播，不能把两套存储看作天然原子一致。

### pgvector：先复用同库，再考虑独立向量系统

项目把 384 维向量与知识数据保存在 PG，用 HNSW cosine 索引支持检索。好处是少维护一套专用向量数据库，关联文档和治理数据方便；代价是向量索引与业务事务共享数据库资源。

HNSW 属于近似索引，存在召回、时延和资源取舍；不能因为建了索引就保证每次执行计划一定使用它。未来是否拆分专用向量库，应根据向量规模、查询延迟、资源争用和过滤需求评估；本次未做专用向量库对照。

### RRF 与规则重排

BM25 分数与向量相似度量纲不同，项目用 RRF 合并名次，再以词项覆盖等确定性信号重排。Parent-Child Chunk 用较细颗粒召回、较完整父块提供上下文，也会增加存储和处理复杂度。

两路融合可能引入噪声；父子切分、融合、重排要分别消融，不能把所有效果笼统归功于 RAG。本次只对检索路径与重排做对照，保持切分相同。

### 实测与边界

默认 Embedding 是本地哈希，不是学过语义的模型。在 10 篇文档、6 条术语、6 条改写、2 条无答案的作者标注诊断集中：

| 方案 | 改写表达 MRR |
|---|---|
| BM25 | 0.7833 |
| 哈希向量 | 0.5333 |
| RRF 混合 | 0.7556 |
| 混合 + 当前规则重排 | 0.7833 |

混合加重排与 BM25 持平，未证明额外质量收益。Top5 在仅 10 篇文档中很宽松，可回答样本全部命中不能外推为真实准确率 100%。四种方案对两个无答案问题均返回候选，检索接口没有据此证明拒答能力。

**面试短答：** ES 负责词项匹配，pgvector 提供另一类候选，混合设计的目标是互补。当前哈希向量实验没有证明优于 BM25，我会先保留单路基线，再用真实语义模型和独立标注集判断双路是否值得。引用 URL 命中也不等于内容支撑答案。

## 8. 指标、日志与链路：按定位问题的需要逐层增加

| 工具 | 当前作用 | 简单替代与代价 |
|---|---|---|
| Micrometer / Actuator | 应用埋点、健康检查与指标暴露 | 框架配套而非独立存储；指标设计和标签需要维护 |
| Prometheus | 抓取并保存时序指标，支持告警规则 | 初期可先看少量关键指标；新增保留周期、基数与查询资源成本 |
| Grafana / Alertmanager | 面板展示、告警展示与通知处理配置 | 面板多不等于定位快；需减少噪声、明确告警对应动作 |
| OpenTelemetry Collector / Tempo | Trace 采集导出、存储与查询 | 单体初期日志 + Request ID 可能足够；采样和存储有成本 |
| Loki / 日志采集配置 | 聚合结构化日志，关联 Trace/Request ID | 小环境可以先本机结构化日志；集中采集需要维护采集链路与存储 |

项目 Compose 使用可选 `observability` profile 启动完整观测栈。先看 HTTP 错误/时延、连接池、Outbox 积压年龄、LLM 降级和检索失败等可采取行动的指标；高基数用户或会话 ID 不应随意作为指标标签。

当前仓库有 Promtail 日志采集配置。本文仅记录仓库现状，不将其描述为已经完成当前生命周期审查的生产采集方案；生产选型与升级需要单独核验。

**面试短答：** 指标帮助发现问题，日志和 Trace 帮助定位原因。完整监控栈不是越多越好，应围绕能执行的故障处理动作建设。项目已接入这些能力，但没有用本地面板或测试阈值证明长期生产 SLO。

## 9. 配套工程工具：避免为了面试扩大架构

| 选择 | 项目用途与理由 | 取舍 |
|---|---|---|
| MyBatis-Plus + 显式 SQL | 简化常规 CRUD，并直接控制关键锁、约束相关查询和 PG SQL | SQL、映射和查询性能需要开发者维护；不宣称比 JPA 必然更快 |
| Flyway | 版本化表、索引和业务约束，使环境升级可追踪 | 迁移执行顺序、锁表和回滚兼容需要设计；不能依赖手工改库 |
| Testcontainers | 验证真实 PG/Redis/Kafka/ES 协作，避免轻量替代数据库掩盖方言/锁差异 | 需要 Docker、启动较慢；不等于真实生产拓扑 |
| Docker Compose | 本地依赖和演示环境便于复现 | 单机方案不自动提供高可用 |
| Kubernetes / Kustomize | 仓库保留部署声明和本地交付演练路径 | 小规模可优先 Compose；生产集群、长期 SLO、发布恢复需要独立证据 |

这些工具分别解决数据访问、迁移、验证和交付问题；本次没有对 ORM、容器编排或日志方案做性能竞赛。模块化单体仍是当前架构，不为展示组件数量而拆分微服务。

## 10. 最后用四句话记住取舍

1. **正确性放在 PG：** 事务保证一起提交，行锁协调同一训练的竞争，约束拒绝重复事实。
2. **缓存服务热点：** 热命中省工作，冷回源增加工作；展示可以接受有限陈旧，业务判断要读真源。
3. **异步不等于 Kafka：** PG worker 也能可靠异步，Kafka 的理由应是独立订阅、分发和回放需求。
4. **双路不等于更准：** 混合检索要用单路消融证明收益，哈希向量不能代表真实语义模型。

复习时逐项回答：不用这个组件能否完成业务？复杂方案多解决了哪个问题？故障时如何退化？什么数据会让我决定删掉它？
