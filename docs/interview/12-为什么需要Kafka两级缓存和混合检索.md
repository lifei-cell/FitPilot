# 为什么需要 Kafka、两级缓存和混合检索

日期：2026-09-17。本文对应当前源码与[隔离对照实验](../performance/architecture-comparison-2026-09-17.md)，不把功能可用、局部测量和生产必要性混为一谈。

## 1. Kafka：先回答为什么异步，再回答为什么选 Broker

**业务问题**：完成训练是用户主操作；PR、统计、通知是派生结果。它们如果全部放在完成事务中，响应要等待派生处理，派生失败还会影响训练事实提交。

| 方案 | 优点 | 成本与适用条件 |
|---|---|---|
| 同事务同步派生 | 逻辑最短；成功返回时派生结果已经提交；少一套后台恢复机制 | 事务更长，下游写失败会回滚主操作；数据量小、派生计算轻、确实需要同步结果时很合适 |
| PostgreSQL 任务表 + worker | 主操作与任务一起落库，后台失败可以重试；无需 Broker | 要实现领取、租期、重试、死信和清理；轮询及积压占数据库资源；少量派生任务通常足够 |
| Outbox + Kafka + Inbox | 将可靠入队与消息分发分开；多个消费组可独立推进、故障隔离和按需回放 | 多一套 Broker、连接、消费位点及排障流程；仍需 Outbox/Inbox，不能因为用了 Kafka 就省掉幂等 |

**本项目采用 Kafka 的设计动机**：训练完成分别驱动 PR 和 Analytics，PR 再驱动通知，代码已有独立消费者。Kafka 提供的价值是把这些订阅者的推进和故障处理分开；“能异步”“任务不因进程退出丢失”并非 Kafka 独有，PG 任务表同样可以做到。

本次对照采用真实 PostgreSQL、Kafka、Outbox Relay 和业务处理器，但 Kafka 侧是单个实验消费者，不测试线上多消费组扩展。同步组保留 Outbox/Inbox，以便尽量固定业务代码；因此不能拿它代表最精简同步 CRUD 的性能下限。

**可以直接这样回答：**

> 我把用户完成训练与 PR、统计、通知的派生处理解耦。Outbox 负责训练事实和事件原子提交，Kafka 负责分发，Inbox 负责重复投递下的幂等。为了验证选型，我还做了同事务、PG 任务表和 Kafka 的隔离对照。异步缩短接受请求的等待，并不等于 Kafka 一定比 PG worker 更快。当前小规模下 PG worker 是合理的简化方案；我保留 Kafka 的理由是演示独立消费者、回放与恢复机制，尚未用生产流量证明其必要性。

追问“现在能去掉 Kafka 吗”：可以做生产适配器迁移，但应保留事务任务、领取保护、幂等和恢复验证；本次 PG worker 是测试适配器，不能直接宣称线上已有无 Kafka 部署模式。

## 2. 两级缓存：先看热点，再看一致性要求

**业务问题**：动作说明等展示数据会重复读取。减少重复查询可以降低数据库压力；如果每次仍要经过网络去 Redis，本机 L1 还能减少这一跳。

| 方案 | 优点 | 成本与适用条件 |
|---|---|---|
| PostgreSQL 直读 | 无失效协议；索引查询简单；关键判断直接读业务事实 | 重复热点读继续消耗数据库连接与查询资源；低负载、低复用率时可能已经足够快 |
| Redis 单层 | 多实例共享缓存，减轻数据库重复读取 | 网络、序列化、回源锁和缓存填充有成本；本地简单主键查询未必比 Redis 慢 |
| Caffeine + Redis | L1 热点命中省掉 Redis 网络请求，L2 提供跨实例共享 | 两层容量与 TTL、跨实例旧值、淘汰和故障回源都需要解释；冷缓存请求可能更慢 |

当前代码用短 TTL 接受展示数据的有限陈旧，关键计划状态仍读数据库。一次实例 A 的 L1/L2 删除，不能删除实例 B 的 L1；“事务提交后删缓存”不等于跨实例强一致。

**可以直接这样回答：**

> 两级缓存主要服务于重复的热点展示读，L1 减少网络往返，Redis 减少数据库重复查询。我做了直读 PG、Redis 单层和两级缓存的冷热对照：热命中和冷回源必须分开看。冷请求需要额外访问 Redis、加锁和回填，可能比直接查 PG 慢。因此我不会把所有接口都缓存；关键业务判断直接读数据库，展示数据才接受短 TTL 旧值。是否保留 L1 要看真实命中率、数据库压力和可接受的旧值窗口。

追问“为什么不只用 Caffeine”：单实例、可丢失且允许陈旧的小热点可以只用本地缓存；共享缓存有助于多个实例复用回填结果，但 Redis 故障时仍要控制回源负载。本次没有测多进程扩容收益，不能把两个缓存对象等同两个生产实例。

## 3. 混合检索：补充召回与排序必须实测

**业务问题**：用户既可能输入 RPE 等精确术语，也可能换一种表达。BM25 和向量检索可能提供不同候选，但多一个通道是否改善结果要靠消融验证。

| 方案 | 优点 | 成本与适用条件 |
|---|---|---|
| BM25 | 对精确术语、字词匹配直接有效；容易查看命中依据 | 表达变化大、缺少共同词时可能召回不足；小型术语库可先采用 |
| 真实语义向量 | 有机会找回词面不同但含义相近的内容 | 取决于模型、领域、语言和数据；需要索引重建、模型成本与质量验证 |
| BM25 + 向量 + RRF | 合并两路名次，避免直接混加量纲不同的原始分数 | 多一次检索与融合，可能引入噪声；需要比两个单路都更好的目标分类收益 |
| 再加当前规则重排 | 用词项覆盖和有限可信度信号调整候选顺序 | 是确定性规则，不是训练过的 Cross-Encoder；也可能偏向词面匹配 |

**关键事实**：项目默认向量来自本地哈希，不是学过语义的模型。它适合离线可复现验收，不能拿它来证明“理解同义表达”。本次补齐 0 权重真正禁用通道的行为，否则仅把贡献分数设零，仍会支付调用成本并引入候选，消融不成立。

**可以直接这样回答：**

> 我设计混合检索是希望术语匹配和语义匹配互补，并用 RRF 合并排序。但我区分了设计动机和效果证据：当前默认哈希向量并不是真实语义模型，诊断集上混合方案没有证明优于 BM25。我会先保留单路作为基线，接入真实 Embedding、重建索引并用独立标注集验证后，再决定是否值得多维护一个检索通道。引用 URL 命中也不等于答案正确，还需要检查内容是否支撑结论。

追问“为何无答案时还返回文档”：TopK 检索本身不是可回答性判断。当前检索接口没有独立的拒答判定，不相关问题也可能拿到候选；不能把“返回了引用”说成“有可靠答案”。这需要另立业务需求和测试，不在本次对照中顺便改变线上行为。

## 4. 面试表达边界

三条统一表达：**业务约束 → 简单方案 → 当前方案增加的能力 → 实测结果 → 增加的成本 → 采用条件**。

- 能说：实现并验证了某条故障路径，或某个明确负载下观察到局部收益。
- 不说：Kafka 天然更快、Redis 一定比数据库快、混合检索一定更准。
- 不说：局部串行调用 P95 是 HTTP 高并发容量，或合成样本指标代表真实用户收益。
- 不预设“复杂方案必须赢”：如果同条件结果不支持，保留简单基线与负例就是选型结论的一部分。
