# FitPilot 项目设计取舍与替代方案

整理日期：2026-09-17。代码基线：`3b5290c`；工作区另有未提交文件，本页只评估已提交架构及明确标注的规划。这里的“为什么不用”表示**当前规模、业务不变量与验证条件下暂不选择**，不表示替代技术普遍较差。既有设计文档能证明方案存在；部分选型动机由当前约束推导，不能伪装成当时的原始决策记录。测试结果需回到各报告绑定的 revision，未在本次重新运行。

答题顺序：**业务问题 → 当前选择 → 替代方案及其更适合的条件 → 本项目的代价/证据边界**。验证步骤见[设计取舍验证矩阵](10-设计取舍验证矩阵.md)。

## 1. 系统形态与持久化

| 设计 | 为什么当前这样选 | 为什么暂不选其他方案；何时重评 |
|---|---|---|
| Java 21 + Spring MVC 单体 | 训练、计划、鉴权与管理 API 主要是同步事务、SQL 和成熟中间件集成；团队可在一个进程内定位与发布。 | WebFlux 只有在依赖与 JDBC 链路也转为非阻塞、且线程/并发实测成为瓶颈时才值得迁移；换语言不能自动解决业务一致性。 |
| 按领域划分模块，保持一个部署单元 | `plan/workout/pr/agent/rag` 有职责边界，同时保留本地事务和低部署成本；用包边界测试约束越层依赖。 | 微服务会引入跨服务事务、网络故障、独立数据库与运维成本；出现独立扩缩容、故障隔离或团队发布瓶颈后，再拆最清晰的异步模块。Spring Modulith 也须证明比现有边界测试多带来收益。 |
| Controller → Application Service → Domain/Repository | HTTP 校验、业务用例事务、领域规则和 SQL 各有归属；事务放在用例边界。 | Controller 直接访问 Mapper 或一个巨型 Service 容易绕过规则、混合事务与接口语义；无需额外复杂的“通用领域框架”。 |
| PostgreSQL 作为业务事实源 | 训练状态、计划版本、用户所有权、回执、事件待发送记录依赖事务、行锁、唯一约束与复杂查询；同库还能承载 pgvector。 | MongoDB/Redis 作为主库会让关系约束与多表事务变难；MySQL也能承载核心业务，但现有 PostgreSQL 的部分索引、JSONB、锁语义与 pgvector 迁移成本不低，不因流行度切换。 |
| MyBatis-Plus + 明确 SQL | CRUD 可复用，Owner 条件、投影聚合、锁与 pgvector 查询仍可精确控制 SQL。 | JPA 适合对象关系导航与自动脏检查；本项目多定制查询，需要审查生成 SQL，换 JPA 未显示收益。MyBatis 的代价是映射/SQL 维护和 N+1 风险。 |
| Flyway 向前迁移，部署时独立 Migration Job | Schema 版本可追溯；多副本应用发布前只执行一次迁移，并可采用 Expand/Contract 保持应用回退兼容。 | 手工改库不可重复；多 Pod 启动各自迁移增加发布耦合；自动 Down Migration 可能破坏新数据。单实例本地开发可让应用自动迁移。 |

依据：[V1 业务/性能设计](../architecture/v1-performance.md)、[V5 交付设计](../architecture/v5-production.md)、`pom.xml`、`src/main/java/com/fitpilot/{plan,workout}/`、`src/main/resources/db/migration/`。

## 2. 核心训练正确性与账户

| 设计 | 为什么当前这样选 | 为什么暂不选其他方案；何时重评 |
|---|---|---|
| 开始训练时复制计划为 WorkoutExercise 快照 | 计划是可变意图，Workout 是历史事实；修改计划后，历史组次、目标和统计口径不变。 | 每次读当前计划虽省存储，却会改写历史语义；只存计划版本 ID 可以实现，但需永久维护所有版本及兼容读取，当前快照更直接。 |
| 状态机 + 数据库部分唯一索引 | 用例层给出友好错误，数据库守住“每人至多一个进行中训练/ACTIVE 计划”等最终不变量。 | 先查再写的应用判断有并发窗口；全局分布式锁依赖外部租约且范围过大。 |
| 计划编辑用乐观锁；组号分配用局部行锁 | 低冲突计划编辑避免长期阻塞，并用 409 让用户处理冲突；同一训练动作的组号短临界区必须串行，唯一约束兜底。 | 全部上悲观锁降低并发；全部靠乐观重试会让组号冲突增多；全局 SERIALIZABLE 提高重试成本。 |
| 查询下推 `userId + resourceId` | 在 SQL 层限定 Owner，读取、更新和 AI Tool 都继承当前 JWT 身份。 | 先按 ID 查再由 Java 判断易遗漏，并会先接触别人的记录；模型传入 `userId` 不可信。 |
| 短期 JWT + 可旋转 Refresh Token（HttpOnly Cookie） | Access 可本地验签；Refresh 可在 Redis 撤销与轮换，浏览器脚本不能直接读取 Cookie 中的长期凭据。 | 只用长期 JWT 难以撤销；服务器 Session 可行但每次校验依赖共享状态；把长期 Token 放 localStorage 增加脚本窃取暴露面。当前 Redis 故障会影响刷新，原生 App 还需重新设计会话传输。 |
| Redis 通用幂等 + 关键写入数据库幂等/回执 | 通用层回放短期成功响应；训练创建和离线记组由数据库唯一性与持久回执承受 Redis 过期、丢失及响应丢失。 | 仅靠 Redis TTL 无法保证跨天或故障后的业务唯一性；只靠数据库不便统一回放 HTTP 响应。业务正确性应始终以数据库为准。 |

依据：[领域与数据库](01-Java-Spring-领域与数据库.md)、[V19 离线回执](../release/workout-auto-recovery.md)、`WorkoutService`、`RecoverableSetService`、`AuthController`、`RefreshTokenService`。

## 3. 前端训练体验与缓存

| 设计 | 为什么当前这样选 | 为什么暂不选其他方案；何时重评 |
|---|---|---|
| React Web 先覆盖手机布局 | 复用同一 REST API 和页面，快速验证训练记录、计划编辑与 AI 闭环。 | 立即双端原生开发会重复实现与验证；需要相机、系统后台任务或稳定原生生命周期时再做原生能力。Capacitor 只是[待实施路线](../roadmap/mobile-app-store-launch-2026-09-16.md)，不是当前已上架能力。 |
| 历史正式组预填，用户点击后才写入 | 降低重复记组输入；预填是建议，用户可改，避免把旧重量误记为本次事实。 | 自动写入最快，却可能制造虚假训练；纯手填操作成本高。需以真实用户记录耗时、误记和撤销来决定。 |
| 本机草稿/队列 + `Client-Operation-Id`/数据库回执 | 手机断网或 HTTP 响应丢失后可复用同一操作编号，重放原回执而不重复加组；与确认输入分离。 | 仅内存会在关页后丢失；仅 Redis 幂等会过期；直接后台同步受浏览器限制。当前 localStorage 可被清理，强离线需求需比较 IndexedDB/原生持久存储。 |
| Service Worker 只缓存静态资源 | 允许已加载的训练页离线重开，同时不缓存 JWT、API 与私有响应，避免旧业务事实被离线缓存误读。 | 缓存所有请求虽然简单，却易泄露和陈旧；不做 Service Worker 则离线重开失败。 |
| 热点展示读用 Caffeine L1 + Redis L2；关键判断直读 PostgreSQL | Caffeine 吸收进程热点，Redis 供实例共享；计划是否仍 ACTIVE、Owner、AI 确认等不变量不能读取可能陈旧的缓存。 | 直接读 DB/仅 Redis 的部署更简单，应在同条件压测中对照；当前无短 TTL 后容量收益证据，不应宣称二级缓存必需。 |
| Cache Aside + 提交后删缓存 + 短 TTL | DB 保持真源；事务提交后删除本地 L1 与共享 L2，其他实例旧值自然过期。 | 写回可能丢业务事实，写穿增加核心写依赖；广播失效/版本化回填能缩短陈旧窗口但需额外协议。当前只承诺有界展示陈旧，不承诺强一致。 |
| 空值缓存、TTL 抖动、重建锁 | 分别抑制不存在 ID 穿透、同时过期和热点重建；锁失效最多重复回源，不影响写入正确性。 | 为缓存重建引入强一致分布式锁、Redlock 或业务级 fencing 成本过高；数据库仍负责最终事实。 |
| Redis Lua 令牌桶；故障时进程内降级 | 多实例统一扣令牌并允许有限突发；Lua 保证读算写原子。 | 固定窗口有边界突刺；漏桶更平滑却不适合容许短突发；网关限流可替代部分应用限流。进程内降级不能维持全局配额。 |

依据：[快速记组](../release/quick-set-recording.md)、[V19 离线恢复](../release/workout-auto-recovery.md)、[短 TTL 缓存](../release/short-ttl-cache-consistency.md)、`web/src/features/workout/`、`TwoLevelCache`。

## 4. 事件、异步任务与恢复

| 设计 | 为什么当前这样选 | 为什么暂不选其他方案；何时重评 |
|---|---|---|
| 完成 Workout 同事务追加 Outbox，派生 PR/Analytics/Notification | 训练事实不应因 Kafka 故障回滚；Outbox 将业务提交与“待发送”原子化，派生结果最终追平。 | 同步放在大事务内会增加完成延迟与故障耦合；DB 提交后直接发送 Kafka 有丢事件窗口。若派生规模很小，数据库任务表可能比 Kafka 简单，仍需同条件对照。 |
| Kafka 作为事件分发与回放层 | 多个消费者独立处理并允许积压、重试和回放；Workout ID 作 Key 使同一聚合进入同一 Topic 分区，但重试/DLT 不保证全链路严格顺序。 | RabbitMQ 更适合任务路由/确认，RocketMQ 也可满足可靠消息；当前没有实测证据证明 Kafka 普遍优于两者。Redis Stream 可做小规模队列，但若依赖保留回放需另评持久性与运维。 |
| 应用轮询 Outbox + `SKIP LOCKED` | 不引入 CDC/Connect 就能多 Relay 批量领取、故障重试；当前可在 PostgreSQL 中直接审计状态。 | 直接发布有双写空隙；Debezium CDC 可减少轮询并提高规模能力，但引入 WAL、Offset、Schema 与 Connect 运维；待扫描/积压成为瓶颈再评估。 |
| `claim_token` 条件续租与回写 | 超时重领后旧 Relay 晚返回不能覆盖新执行者数据库状态。 | 只按 ID/status 回写有竞态；单纯增加超时时间不能消除。UUID 是领取身份，不是可由 Kafka 拒绝旧写的单调 fencing 序号，也无法撤回已发消息。 |
| Inbox + 业务唯一约束，接受至少一次投递 | Kafka 已收到但 Outbox 未标记时会重发；每个消费者在其业务事务内去重，投影自身再加唯一约束。 | Kafka Transaction/EOS 主要覆盖 Kafka 内部链路，不会自动使外部 PostgreSQL 副作用 Exactly Once；不应宣称端到端精确一次。 |
| 退避重试 + DLT/数据库死信 + 人工回放 | 临时故障自动恢复，毒消息隔离并保留可审计修复入口。 | 无限重试会堵住后续消息；直接丢弃无法追责。回放前必须修复根因，也可能改变局部顺序。 |

依据：[V2 事件架构](../architecture/v2-events.md)、[V20 领取保护](../release/outbox-claim-ownership.md)、`WorkoutService.complete`、`OutboxRelay`、`ProcessedEventRepository`。

## 5. RAG、Agent 与模型

| 设计 | 为什么当前这样选 | 为什么暂不选其他方案；何时重评 |
|---|---|---|
| PostgreSQL 文档真源 + ES 可重建 BM25 索引 | 版本、来源、许可证、生命周期与 Chunk/向量需要事务化保存；ES 负责词法检索，故障可重建。 | 全存 ES 会把业务真源交给索引系统；仅 PostgreSQL 全文检索更简单，应先比较词法效果、成本和数据量，双引擎有维护代价。 |
| Parent-Child Chunk、BM25 + pgvector 双路召回 | Child 提高局部命中，Parent 保留上下文；术语匹配与语义近邻覆盖不同问法。 | 整篇向量容易稀释细节；纯 BM25 漏同义表达，纯向量可能漏精确术语。但双路是否真的更好，需要固定数据集和真实 Embedding 对照；默认本地哈希只适合离线可运行性。 |
| RRF + 确定性 Rerank + Citation | BM25 与向量原始分数不可直接相加，RRF 用排名融合；确定性规则成本低、可复现；返回来源便于核查。 | LLM/交叉编码器重排可能提高质量，但会增加时延与成本；直接回答不附引用难以审核。Citation Validity 只说明引用来自检索上下文，不代表引用支持结论。 |
| 文档版本、删除传播与反馈先审核再离线实验 | 避免过期/撤销文档被返回；不让恶意或噪声负反馈立即改在线排序；实验冻结文档和样本版本。 | 直接拿在线负反馈自动调权更快，但易被污染、难复现；需要人工审核成本，规模扩大后可设计抽样审核。 |
| 显式单 Agent Workflow + 只读 Tool 白名单 | 当前意图、取数、提案与确认可按有限步骤执行；Tool 继承 JWT Owner，不让模型直接触碰 Repository。 | 自由循环或 Multi-Agent 增加路由、共享状态、循环、费用和追责难度；只有单流程无法解决可衡量任务时才拆。纯规则足以覆盖简单任务，必须用真实模型评测证明 Agent 增益。 |
| 模型只提议；后端 Guardrail + 用户一次性确认 + 新 DRAFT | 身份、状态和训练安全规则由可审计的后端控制；确认时重新校验版本，原 ACTIVE 计划保持可用。 | 模型直接写库/直接改 ACTIVE 会绕过 Owner、过期计划和用户意图，错误恢复困难；只生成自由文本虽更简单，但不能闭合计划调整用例。 |
| PostgreSQL 会话真源 + Redis 近期缓存 | 跨设备历史与待确认动作可恢复，Redis 只加速最近消息读取。 | 仅 Redis 易因淘汰或故障失去历史；只 PostgreSQL 在低流量下更简单，是否需要缓存应测会话读热点。全部对话塞入 Prompt 增成本且触及上下文上限。 |
| 主备模型/重试/熔断/规则回退，共享 Deadline | 外部模型不稳定时限制尾延迟与并发，降级仍走同一业务校验链；审计记录模型、成本与失败。 | 单 Provider 更省运维，故障可明确提示；多级路由只有在真实可用性和单位成功成本改善时才值得保留。Mock Provider 只能证明协议与容错，不证明真实质量。 |
| MCP 做薄适配器，复用 REST 用例 | 多种客户端仍走同一鉴权、Tool 白名单、确认及审计。 | 在 MCP 层另写一套业务逻辑会形成安全与事务分叉；若没有真实 MCP 客户端需求，保持 REST 即可，不能把“支持协议”当用户价值。 |
| 规则拦截、留存/转化/调整前后指标 | 让拒绝原因、模型费用和观察窗口可回查，避免只展示“调用成功”。 | 只看模型输出或测试通过不能说明用户受益；前后变化也不是因果证明，需真实用户对照和风险指标。 |

依据：[V3 检索](../architecture/v3-rag.md)、[V4 Agent](../architecture/v4-agent.md)、[V5 模型容错](../architecture/v5-production.md)、[V6 产品闭环](../architecture/v6-ai-product.md)、[AI 指标验收](../release/ai-product-value-metrics-validation.md)。

## 6. 测试、观测与交付

| 设计 | 为什么当前这样选 | 为什么暂不选其他方案；何时重评 |
|---|---|---|
| JUnit/Mockito + Testcontainers + 浏览器关键 E2E | 纯规则用单测，PostgreSQL 锁/索引、Redis、Kafka、ES 用真实容器，端到端验证少量核心用户流程。 | 只用 H2/Mock 快，却无法覆盖 pgvector、部分索引与真实 Broker；全靠 E2E 慢且易脆。测试通过只证明覆盖场景。 |
| 零跳过/覆盖率门禁 + ArchUnit | 防止绿色构建遗漏集成测试、关键包未执行和模块边界被意外破坏。 | 只看覆盖率容易写空断言；固定 100% 指标带来低价值测试。应补故障与行为断言，而非追数字。 |
| 指标、日志、Trace 和低基数标签 | 将 HTTP、Agent、LLM、RAG 与异步消息串起来，观察长尾、错误、成本和积压年龄。 | 只看平均延迟/日志难定位跨组件故障；全量记录用户文本和高基数 ID 会增加隐私与成本。仪表盘是否有用还需故障发现/恢复时间验证。 |
| Compose 本地联调；Kustomize/Kubernetes 作为交付方案 | Compose 可快速启动依赖；K8s 清单表达多副本、独立迁移与滚动升级；镜像按不可变 Digest 追溯。 | 小规模/预算受限的封闭试用，受限且安全配置的生产 Compose 可能更省成本；K8s 不能自动证明高可用。当前真实 Production Delivery Gate 为 `SKIPPED`。 |
| CI→Release 精确 SHA、SBOM/扫描、迁移后部署 | 测试、源码、镜像 Digest 与交付证据一一对应；过期 CI 不应发布到最新标签。 | 浮动 `latest` 难回溯，手工跳过门禁易发布未经验证版本；扫描和 SBOM 不能证明业务正确或零漏洞。历史 V18 远端结果不可替代 V19/V20 发布。 |
| Redis 故障降级与 Readiness 当前包含 Redis | 应用代码可回源 DB，同时 Pod 在 Redis 失效时可能摘流；这里存在“继续服务”与“保护数据库”的取舍。 | 不应同时声称 Redis 宕机时生产仍对外可用；先做 Redis 故障下的 DB 容量实验，再决定 Readiness 是否移除 Redis 或保守摘流。 |
