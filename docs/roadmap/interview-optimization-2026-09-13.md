## 优先级与验收

| 优先级 | 优化 | 当前依据 | 完成标准与面试价值 |
|---|---|---|---|
| P0 | 多实例缓存一致性 | `TwoLevelCache.evict` 只删除当前实例 L1 与 Redis L2；其他实例已命中的 L1 仍可返回旧值。提交后删除也不自动消除并发旧读回填 | 两实例复现 A 更新、B 旧读；明确各类数据可容忍的陈旧窗口。评估可变资料/ACTIVE 计划退出 L1，与失效通知、短 TTL、版本化回填方案的成本。覆盖通知丢失、Redis 中断及恢复、读写交错；强一致业务判断仍读数据库 |
| P0 | Outbox 领取所有权与积压恢复 | `claimBatch` 支持超时重领，但 `markSent` 仅按 id/status，`markFailed` 仅按 id 更新，没有领取 token。旧执行者晚返回可能覆盖新领取者状态；relay 批量领取后逐条等待发送 | 先复现 A 超时、B 重领、A 晚成功/失败。增加领取 token 或版本条件更新，检查影响行数；控制领取量与发送耗时，必要时续租。旧执行者不能改写新领取状态。注入发送成功但未标记、消费者提交后未 ACK、Kafka 恢复等故障，验证业务不重复和积压可追平 |
| P1 | 当前版本写链路性能证据 | 历史热点读是短时预热缓存场景；已有 30 分钟混合压测属于历史 V5，不能直接证明 V19 离线回补容量 | 针对加组、完成训练、离线批量回补、历史查询构建数据量阶梯和稳态/突发模型。记录提交 SHA、配置、数据量、P95/P99、错误率、丢弃迭代、数据库锁等待/连接池、JVM 与积压年龄；找到一个真实瓶颈并提供同条件前后对照 |
| P1 | 真实 AI 质量与成本基线 | V18 报告明确 Mock Provider 验收不能证明真实模型质量；默认 embedding 为本地确定性实现 | 在明确外发数据与预算后，以脱敏、独立留出的测试集比较规则、真实模型、检索配置；记录工具正确率、越权/危险写入拦截、Recall/MRR、引用有效性、P95 和每次成功成本。人工复核引用是否支持结论，固定模型/提示词/数据集版本；不预设提升数字 |
| P2 | 离线恢复的真实使用与冲突体验 | V19 已覆盖响应丢失重试、账户隔离、冲突保留与导出；跨设备结束后的冲突需要人工核对 | 先做本人及少量自愿用户的手机训练试用，记录待同步时长、恢复成功率、重复写入和冲突样例。明确浏览器存储回收边界，再决定是否需要 IndexedDB 或原生端；任何转存到新训练都需用户确认，不能静默改变历史 |

## 实施顺序

Java 后端面试优先完成缓存与 Outbox 两个可复现并发案例，再补当前写链路性能报告。AI 应用后端岗位可将真实 Provider 评测提前。每项独立提交，实现、测试、故障证据与文档一起完成。

Outbox 的领取 token 只约束数据库状态回写，无法撤回已发送的 Kafka 消息；仍保留 Inbox 和业务唯一约束，表述为至少一次投递与幂等业务效果。Kafka 外部数据库写入的语义边界参考 [Kafka 官方设计文档](https://kafka.apache.org/design/)。

SQL 瓶颈用 `EXPLAIN (ANALYZE, BUFFERS)` 观察实际执行与缓冲访问，参考 [PostgreSQL 17 官方说明](https://www.postgresql.org/docs/17/using-explain.html)。执行 ANALYZE 会运行语句，写语句分析应在隔离测试环境进行。

## 面试交付物

每个优化保留一页材料：业务问题、失败时序、原方案边界、候选方案取舍、实现及测试入口、前后测量、剩余限制。优先把三条主线讲透：训练写入可靠性、异步派生数据一致性、受控 AI 决策。微服务拆分、分库分表、Multi-Agent 或原生 App 应由实测瓶颈与用户需求触发。
