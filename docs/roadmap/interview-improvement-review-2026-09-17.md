## 按收益排序

1. **P0：统一训练写操作的状态与锁协议。** `WorkoutService.addExercise` 先读状态再插入，没有像 `addSet/updateSet/deleteSet/complete/cancel` 一样锁住所属 Workout；`nextExerciseSequence` 读取最大序号再加一。存在状态检查后另一事务完成/取消训练、原请求随后插入动作，以及并发分配相同序号的风险。数据库唯一约束可拒绝重复序号，但不能代替状态协议。建议先用真实 PostgreSQL、两个事务与屏障复现；再统一父行锁、锁内检查状态与序号分配，明确冲突响应。验收关注提交后的业务不变量，不只验证接口状态码。
2. **P1：当前写链路性能闭环。** 以加组、完成训练、离线回补为负载，在多档数据量下采集 P95/P99、错误率、吞吐、锁等待、连接池及 JVM 指标。结合 SQL 执行计划或剖析定位一个真实瓶颈，保留同条件前后对照。历史 V1 热点读与 V5 混合报告不能证明当前 V19/V20 写链路容量。
3. **P1：Outbox 积压恢复与背压。** token 保护已经完成；当前 Relay 仍逐条等待 Kafka Future。默认一次领取 100 条、发送超时 5 秒、领取超时 30 秒，慢发送可能让批次尾部等待过久并被其他实例重领。先测 Kafka 中断恢复、双实例竞争及投影追平时间，再决定缩小批次或引入有界并发。并发方案须保留 token 条件回写、Inbox 幂等，并明确同聚合顺序需求。报告积压年龄、恢复速率及重复投递，不能声称 Exactly Once。
4. **P1：真实 AI 的质量与成本证据。** 默认确定性 embedding 和 Mock Provider 测试不能证明真实语义检索或模型效果。用合成或获授权的脱敏数据、独立留出集比较规则/真实模型及 BM25/向量/Hybrid；记录 Recall、MRR、人工核对的引用支撑率、工具选择与越权拦截、P95、每次成功成本。真实外发和费用另行明确授权；本次没有调用。
5. **P2：验证复杂选型是否值得。** 先挑最可能被追问的一项做对照，例如同步派生、PG 任务表和 Kafka，或数据库直读、Redis 与两级缓存。比较性能、故障隔离、资源和维护成本；没有收益也保留结果并说明采用条件。已有 ArchUnit 规则，无需重复建设架构门禁。
