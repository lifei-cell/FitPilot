# FitPilot：从业务约束反推设计

日期：2026-09-17。代码基线：`9ba05d9`。本页根据现有源码、功能报告与项目取舍文档整理，是**当前项目的重新审视与下一步验证顺序**，不是对过去研发过程的事后改写。本次未进行用户访谈、新压测或真实模型评测。

## 1. 先把用户问题说清楚

**目标用户假设**：在健身房按计划做力量训练、需要逐组记录重量和次数，并会回看上次成绩调整负荷的人。尚无真实用户访谈或使用数据证明该人群的规模、付费意愿或当前方案更好。

**待验证痛点**：逐组输入打断训练；弱网、锁屏、刷新后无法判断组是否保存；计划调整缺少对近期训练事实的解释，AI 建议又可能写入过期或不合适的计划。前两项已有功能与本地故障测试，仍需真实用户使用证据；第三项只有规则/流程与受控样本，缺真实模型质量和用户收益证据。

**最小业务闭环**：`建立计划 → 开始训练并生成快照 → 快速记录组 → 完成训练 → 查看历史/PR → 用户决定是否调整计划`。没有 Agent、RAG、Kafka 或双层缓存，这条闭环也应成立。

## 2. 用业务问题排序，而不是按技术栈排序

| 优先级 | 真实约束或假设 | 当前实现和可说明的价值 | 目前不能宣称的结论 |
|---|---|---|---|
| 核心正确性 | 历史训练不能被修改后的计划污染；同一组重试不能多写；用户只能改自己的数据。 | Workout 快照、状态机、Owner 查询、数据库唯一约束和 V19 持久回执直接守住这些不变量。 | 本地通过的场景不等于任意浏览器、任意生产故障下零丢失。 |
| 训练体验 | 逐组操作要足够快；中断后要知道哪些组已保存。 | 历史正式组预填、点击确认、草稿和离线队列形成可操作闭环。 | 没有真实用户任务时间、误记率和复用率，不能说体验已经优于现有 App。 |
| 派生能力 | PR、分析和通知可以晚于训练完成，但最终应追平。 | Workout 与 Outbox 同事务、Kafka 派生和 Inbox 去重能处理指定故障。 | Kafka 相比同步更新或 PostgreSQL 任务表在当前规模更经济，仍需对照。 |
| 热点读取 | 如训练历史/动作详情读量使数据库成为瓶颈，缓存才有容量价值。 | 当前有 Caffeine + Redis 和短 TTL 陈旧收敛设计。 | 历史短时热点读不证明短 TTL、多实例、混合流量下仍需两级缓存。 |
| 知识辅助 | 用户问训练术语或知识来源时，需要可核查的外部资料。 | RAG 检索知识文档并返回引用；训练历史与调整事实来自 PostgreSQL 业务 Tool。 | “根据训练历史生成建议所以必须 RAG”不成立；双检索优于单检索、引用支持结论均待真实评测。 |
| 计划调整 | AI 的错误提案不能直接改 ACTIVE 计划。 | 单 Agent/规则工作流只提议，后端 Guardrail、一次性确认和新 DRAFT 负责最终写入。 | 安全链正确不代表模型建议有训练效果；受控样本指标也不证明真实改善。 |
| 交付运营 | 只有存在真实外网用户与恢复目标时，生产部署复杂度才有用户价值。 | CI/Release、镜像 Digest、K8s/Kind 演练和 Runbook 提供工程准备。 | 真实 Production Delivery Gate 仍是 `SKIPPED`，不能讲成已在生产长期运行。 |

## 3. 从今天起的演进门槛

1. **先让主流程被真实使用**：招募少量目标用户完成真实训练任务，记录每组操作时间、改错次数、未同步组和冲突；对照手动记组。先记录基线，再事先写下改进目标。小样本只用于发现问题，不作市场或疗效结论。
2. **再守住业务不变量**：在相同版本和数据库下重放断网、响应丢失、重复提交、跨设备结束。已确认组与数据库事实逐条核对；失败要可恢复或导出。这一步决定 V19 回执是否真正解决记录可靠性。
3. **再判断中间件是否值得保留**：用同数据、同负载比较直读/单层/双层缓存，以及同步派生/数据库任务表/Kafka。看用户延迟、P95/P99、积压追平、数据库资源与运维成本。结果不支持增益时，简化比“保留技术亮点”更合理。
4. **最后验证 AI 是否增加价值**：先比较规则建议与真实模型建议；知识问题另比较 BM25、向量和双路检索，人工检查引用是否支持结论。记录拒绝原因、错误建议、时延和单次成功成本；在安全门槛通过后才做小流量用户对照。

## 4. 固定的一页设计约束

```text
目标用户：力量训练中逐组记录并回看历史的人（待访谈验证）
核心痛点：记组中断、保存结果不确定、调整依据不清（各自待量化）
最小闭环：计划 → 训练快照 → 逐组记录 → 完成 → 历史 → 人工调整
现有替代：纸笔/表格/现有健身 App；本项目相对收益待对照
当前规模：DAU、每日训练量、数据量、真实模型请求量均未取得生产证据
正确性底线：不串用户；确认写入不重复；未确认 AI 提议不写 ACTIVE
业务指标：记录一组耗时、失败恢复率、建议采用与拒绝原因、留存
工程指标：写入错误、P95/P99、派生追平时间、旧缓存窗口、单次成功成本
升级条件：先测到用户痛点或系统瓶颈，再评估相应组件；未测到则简化
```

## 5. 面试表达边界

可以说：“我把训练记录可靠性和 AI 写入可控性作为两条主线。先用数据库事务、约束、快照与回执保证事实正确；异步投影和缓存是针对可容忍延迟的读取/派生能力。Kafka、两级缓存和双路检索已经实现，但当前规模下的必要性还需与简单方案同条件对照。RAG 为训练知识提供来源，不负责读取用户历史；用户历史来自受 Owner 约束的业务 Tool。真实用户收益、真实模型质量和生产运行仍在验证。”

不应编造“用户量增长后才引入 Kafka/缓存”“统计查询已被真实流量压垮”“LLM 慢所以当前 Agent 已改异步”等仓库没有证据支持的演进故事。`docs/architecture/v1-v6` 是版本功能演进，不能自动解释为真实需求驱动。设计细节与替代方案见[设计取舍手册](../interview/11-项目设计取舍与替代方案.md)，实验对照见[验证矩阵](../interview/10-设计取舍验证矩阵.md)。
